# Cove — Product Roadmap v2.0

Кроссплатформенное приложение для хранения файлов в собственном зашифрованном
контейнере `.slr`. Медиатека + файловый менеджер + веб-доступ, с упором на
безопасность и производительность на больших коллекциях (100 000+ файлов).

## Стек

| Компонент | Язык / технология | Почему |
|---|---|---|
| **Core** (формат `.slr`, крипто, файловая таблица, индекс поиска) | **Rust** | Безопасность памяти критична для крипто-кода; один источник истины, переиспользуется везде через биндинги |
| Desktop GUI (Windows/Linux) | **Python + PySide6 (Qt)**, вызывает Core через **PyO3** | Быстрая разработка UI, зрелая экосистема Qt |
| Android GUI | **Kotlin + Jetpack Compose**, вызывает Core через **UniFFI** | Нативный доступ к Keystore/биометрии, нормальный сенсорный UX |
| Web-интерфейс | **Rust (Axum)** backend напрямую использует Core-крейт + **TypeScript/Svelte** frontend | Без FFI-накладных расходов на бэкенде, лёгкий фронт |
| Сборка/CI | GitHub Actions, `cross`/`cargo-ndk` для Android-таргетов | Кроссплатформенные сборки из одного пайплайна |

Криптопримитивы — через `RustCrypto` / `orion` / `argon2` крейты (аудированные
реализации, не писать крипто-примитивы руками).

## Фаза 2. Контейнер `.slr`

**Цель:** собственный формат файла-контейнера.

> Полная спецификация (байтовая раскладка Header/Keyslots/Commit Pointer/
> File Table/Data Blocks, схема атомарности, что хранится вне контейнера) —
> [docs/FORMAT.md](docs/FORMAT.md). Ниже — только сводка.

```
.slr layout:
  Header          (magic, версия формата, параметры KDF, соль)
  Metadata        (зашифровано: настройки контейнера)
  Users           (зашифровано: список пользователей, wrapped-ключи)
  File Table      (зашифровано: имена, пути, атрибуты, чек-суммы)
  Search Index    (зашифровано: индекс для быстрого поиска)
  Data Blocks     (зашифровано чанками — см. Фазу 3)
  Free Block Map
  Footer          (контрольные суммы, указатель на актуальную File Table)
```

Ключевые архитектурные решения (закрывают пробелы из черновика v1.0):

- [x] **Header/Keyslots/Commit Pointer/Superblock/File Table/Free Block Map**
      реализованы по байтам как в FORMAT.md, с честными round-trip тестами
      (25 тестов в `cove-core`, включая полный интеграционный цикл
      create→close→reopen→unlock→unlock_with_recovery). Формат кода — ручная
      little-endian (де)сериализация через общий `format::wire` (без serde/
      bincode — контроль над байтовым layout'ом важнее удобства)
- [x] **Атомарность записи**: `Commit Pointer` A/B с двойной буферизацией
      реализован и покрыт тестом на "торн" записи (`torn_write_detected`);
      `close()` всегда пишет в неактивный слот, `fsync` после данных и после
      указателя отдельно — FORMAT.md §6a
- [x] **File Table и имена файлов зашифрованы** постранично
      (`MAX_ENTRIES_PER_PAGE=4096`), домены HKDF-подключей вынесены в один
      модуль (`crypto::keys::domain`), чтобы писатель/читатель не разъехались
- [x] **Recovery-keyslot** реализован как полноценная альтернатива входу по
      паролю — 12-словная BIP39-фраза (крейт `bip39`), проверено тестом
      `wrong_recovery_phrase_fails`
- [x] Создание / открытие / закрытие контейнера — реализовано и покрыто
      интеграционным тестом
- [ ] Смена версии формата с миграцией — отложено до появления второй версии формата
- [x] Восстановление при **частичном** повреждении File Table (потеря одной
      страницы среди многих) — сделано задним числом, см. отдельную запись
      ниже (после Фазы 18)
- [x] Компактификация (сборка мусора) свободных блоков — сделано задним
      числом, см. отдельную запись ниже (после Фазы 18)
- [x] Постраничная запись "только тронутой страницы" File Table — сделано
      задним числом, см. отдельную запись ниже (после Фазы 18)

## Фаза 3. Криптография

**Цель:** envelope-схема шифрования с поддержкой смены пароля и recovery.

```
Пароль пользователя
      │  Argon2id (параметры бенчмаркаются под целевое железо,
      │  отдельно для десктопа и слабых Android-устройств)
      ▼
  Key Encryption Key (KEK)
      │  оборачивает (wrap)
      ▼
  Data Encryption Key (DEK)  ──▶ шифрует Data Blocks (XChaCha20-Poly1305, чанками)
      │
      └─ у каждого пользователя — свой wrapped DEK (свой KEK от своего пароля),
         что даёт multi-user доступ к одному контейнеру без шеринга пароля
```

- [x] Argon2id для KDF — параметры конфигурируемые (`KdfParams`), но
      реальный бенчмаркинг под целевое железо (в т.ч. слабые Android-
      устройства) — задача для стенда с реальными устройствами, не
      юнит-теста; текущие значения (19 MiB / 2 итерации) — OWASP-минимум,
      отправная точка
- [x] Envelope encryption: `change_password()` перешифровывает только один
      keyslot (точечная запись на диск), остальной контейнер не трогается —
      проверено тестом `change_password_then_old_password_rejected`
- [x] **Recovery key** — 12-словная BIP39-фраза, отдельный keyslot,
      разблокировка ею работает наравне с паролем (Фаза 2)
- [x] Multi-user: `add_user`/`remove_user` реализованы, у каждого свой
      wrapped DEK + роль; инвариант "нельзя удалить последнего админа"
      проверен тестом
- [x] Безопасное удаление ключей из памяти — `zeroize` на `Dek` через
      `ZeroizeOnDrop` (Фаза 1); `mlock`/`VirtualLock` — платформенная задача,
      не блокирует остальной прогресс, отложена до GUI-интеграции
- [ ] Целостность: AEAD уже аутентифицирует каждую страницу/блок отдельно —
      отдельный MAC/хэш **всей** File Table поверх этого признан избыточным
      на данном этапе (не даёт защиты сверх того, что уже даёт постраничная
      аутентификация); пересмотреть, если появится конкретный сценарий,
      который это не покрывает

## Фаза 4. Пользователи

```
Первый запуск → создание администратора → генерация recovery key
      → создание Users-раздела внутри контейнера → авторизация → открытие контейнера
```

- [x] Логин/пароль — реализовано (Фаза 2); требования к сложности пароля —
      это UI-валидация поверх Core (Фаза 5/GUI), Core сознательно не
      навязывает политику паролей на уровне формата
- [x] Смена пароля — быстрая, т.к. перезаписывается только один keyslot
- [x] Роли (admin/read-write/read-only) — `Role` enum, проверяются через
      `require_admin()` на `add_user`/`remove_user`. Enforcement для
      read-only на файловых операциях — добавится вместе с самими
      операциями в Фазе 6 (сейчас там `todo!()`, проверять нечего)
- [x] Добавление/удаление пользователей — точечная запись slot'а на диск,
      не переписывает остальные 15 слотов ни при каких обстоятельствах
- [x] Журнал входов — но только **успешных** разблокировок: закодировать
      неудачную попытку нечем шифровать (DEK ещё не получен на этот
      момент). Учёт неудачных попыток осмысленно делать вместе с лимитом
      попыток — это уже следующий пункт
- [ ] Автоблокировка по таймауту, лимит попыток входа — это состояние
      живёт в GUI-сессии (таймер, счётчик до перезапуска), а не в формате
      контейнера; сознательно отложено до Фазы 12 (Настройки → Безопасность),
      где оно и было изначально запланировано

## Фаза 5. GUI (Desktop)

- [x] Окно входа (`LoginDialog`, вход по паролю и по recovery-фразе),
      главное окно (`MainWindow`), настройки (`SettingsDialog`), диалоги
      создания/добавления пользователя/смены пароля/recovery-фразы,
      меню "Пользователи"/"Сессия" — реализовано и покрыто офскрин-смоук-
      тестом всего потока (создание → вход → add_user → смена пароля →
      смена темы → выход), см. `scripts/build_python_bindings.sh`
- [x] Тёмная/светлая тема — реально переключаемая (`app/theme.py`,
      QSS-стили + `QApplication.setStyleSheet`), сохраняется в
      `app/config.py` вне контейнера (как и решили в FORMAT.md — настройки
      приложения не привязаны к конкретному `.slr`)
- [x] Главное окно: сайдбар со всеми разделами (Библиотека / Фото / Видео /
      Документы / Избранное / Недавние / Корзина / Мои файлы) + Настройки.
      Список файлов реально дёргает `list_dir()` из Core — сейчас везде
      пусто, т.к. `import_file` и остальные файловые операции ещё
      не реализованы (Фаза 6), это честный empty state, а не заглушка

**Попутно закрыт скрытый пробел Фазы 1**: PyO3-биндинги до этой фазы
экспортировали только `core_version()` — реального доступа к `Container`/
`LockedContainer` из Python не было. Теперь `bindings/python` оборачивает
весь публичный фасад (`create`/`open`/`unlock`/`unlock_with_recovery`/
`add_user`/`remove_user`/`change_password`/`list_dir`/`login_history`/
`close`) с маппингом ошибок на Python-исключения по ARCHITECTURE.md §3.

**Известное упрощение**: сборка `.so` — через `scripts/build_python_bindings.sh`
(`cargo build --release` + копирование), не через `maturin` — система
CachyOS защищена PEP 668 (`externally-managed-environment`), а
`pip install maturin --break-system-packages` сознательно не делали.
Перейти на `maturin`/venv — отдельная, несрочная задача Фазы 16 (Сборка).

**Пересмотр после Фазы 12 — поток входа упрощён по прямой просьбе
пользователя.** Раньше: "Открыть хранилище" (выбор `.slr`-файла) →
`LoginDialog` с выпадающим списком пользователей. Теперь: `WelcomeWindow`
запоминает "основное" хранилище (`config.py: default_container`) и при
следующем запуске сразу показывает форму логина — только логин (свободный
текст, не список) и пароль, без выбора файла. Экран "Создать"/"Открыть"
остаётся доступен под формой входа (если её отменить) — так что завести
новое хранилище или открыть другое по-прежнему можно.

Осознанный компромисс с приватностью: путь к хранилищу раньше запоминался
только по опциональной галочке `remember_recent` (см. FORMAT.md — "путь
может выдавать факт существования тайника"). `default_container`
запоминается **всегда**, не по галочке — иначе "просто спросить логин и
пароль" не работает технически (без файла нечем проверить пароль — из него
выводится ключ расшифровки конкретного keyslot'а). Это не забытая деталь,
а сознательно принятый по просьбе пользователя компромисс "удобство в обмен на приватность".

Добавление пользователя в **другое** (не текущее открытое) хранилище
сознательно не реализовано в этом заходе — потребовало бы параллельной
аутентификации во второй контейнер прямо из диалога добавления пользователя,
это отдельная, более рискованная фича, и не было достаточной ясности, что
именно нужно. `ManageUsersDialog`/`AddUserDialog` по-прежнему работают
только с текущим открытым контейнером.

## Фаза 6. Работа с файлами

- [x] Импорт, экспорт, удаление, переименование — реализовано в Core
      (чанкирование по `block_size`, каждый блок — самостоятельная запись
      `[plaintext header][AEAD ciphertext]`, byte-offset'ы в `FileEntry.block_list`)
      и в GUI (контекстное меню, меню "Файл"). `read_at`/`file_size` тоже
      сделаны здесь, а не отложены до Фазы 7 — `import_file` не на чем было
      бы честно проверить, кроме как прочитав обратно
- [x] Папки и подпапки — `is_folder` бит в `FileFlags`, `create_folder`,
      навигация в GUI (двойной клик внутрь, "⬆ Вверх" по стеку пройденных
      папок)
- [~] Drag&Drop — импорт файлов из ОС в текущую папку **реализован в коде
      правильно** (стандартный Qt-паттерн: `dragEnterEvent`/`dropEvent`
      переопределены в настоящем Python-подклассе `QListWidget`/`QLabel`
      через общий `_DropTargetMixin`, а не подвешены атрибутами на голый
      экземпляр — так они не были бы. Оба виджета контента, и список файлов,
      и плейсхолдер "здесь пока пусто", размечены как drop-цель, т.к. Qt
      адресует событие тому, что реально под курсором). **Но на среде
      разработки не работает** — событие `dragEnterEvent` не доходит до
      приложения вообще, ни под нативным Wayland, ни под принудительным
      X11/XWayland (`QT_QPA_PLATFORM=xcb`), что указывает на ограничение
      уровня сессии/композитора, а не баг в коде Cove (подтверждено
      диагностикой с временным логированием событий — оно так и не
      печаталось). Не разбирались до конца, требуется тест "работает ли
      DND вообще между двумя другими приложениями на той же машине" —
      отложено, рабочая альтернатива (диалог импорта) есть и используется
- [x] Корзина — `delete_file` на нетронутой записи прячет её (`trashed=true`,
      восстановимо через `restore_file`), повторный `delete_file` на уже
      спрятанной — окончательно снимает ссылку из File Table. Блоки данных
      удалённых/перезаписанных файлов остаются на диске орфанами
      (зашифрованы — не утечка) до компактификации в Фазе 15, как и
      планировалось изначально
- [x] Открытие во внешнем приложении — экспорт во временный файл +
      `QDesktopServices.openUrl`, ре-импорт — **вручную** через
      `replace_file_content` по кнопке "Да" в диалоге после редактирования
      (не автоматическое отслеживание изменений файловой системы — это
      сознательное упрощение, а не забытая деталь)

**Ещё один реальный баг, найденный при живом тестировании**: диалоги выбора
файла (`QFileDialog.getOpenFileName(s)`/`getSaveFileName` — открытие/создание
хранилища, импорт, экспорт) иногда не реагировали на клик вообще. Причина —
нативный диалог на некоторых системах идёт через `xdg-desktop-portal` и
может открыться за главным окном или не открыться вовсе, без ошибки. Фикс —
`QFileDialog.Option.DontUseNativeDialog` на всех четырёх местах вызова:
переключает на собственный Qt-диалог, который не зависит от портала.

**Побочный эффект**: разделы "Фото"/"Видео"/"Документы"/"Избранное"/
"Недавние" в GUI сейчас показывают честную заглушку
("виртуальные разделы появятся в Фазе 10"), а не фильтруют реальные файлы —
фильтрация по типу требует инфраструктуры виртуальных разделов из Фазы 10,
которой ещё нет. "Библиотека" и "Мои файлы" пока показывают одно и то же
(корень дерева папок) — различие между ними тоже придёт с Фазой 10.

## Фаза 7. Просмотр

## Фаза 13. Web-интерфейс

```
Авторизация → главная страница → библиотека → просмотр → поиск → загрузка → удаление
```

Отдельная поверхность атаки — свой мини-threat-model:

- [x] Rate-limiting / защита от брутфорса логина — фиксированное окно
      10 попыток / 15 минут на IP (`state.rs`), после лимита `429`, честно
      протестировано curl'ом до 11-й попытки
- [x] CSRF-защита, безопасные сессионные токены — session-кука
      (32 случайных байта, base64) отдельно от CSRF-токена (тоже 32 байта),
      CSRF обязателен через заголовок `X-CSRF-Token` на всех методах кроме
      GET/HEAD — проверка встроена прямо в экстрактор `AuthedSession`
      (auth.rs), так что любой хендлер получает защиту просто через
      сигнатуру, без ручных проверок внутри
- [x] HTTPS с самоподписанным сертификатом для LAN — генерируется через
      `rcgen` один раз и кешируется на диске (`~/.local/share/cove/`),
      а не при каждом запуске, иначе браузер терял бы доверие к отпечатку
      каждый перезапуск сервера. `--http` — только для разработки/за
      реверс-прокси, явно помечен предупреждением в логе при старте
- [x] По умолчанию **выключено**, явное включение в настройках с
      предупреждением — сервер не встроен в основной процесс десктоп-GUI:
      это отдельный бинарник `cove-web-backend`, десктоп запускает его как
      дочерний процесс только по нажатию "Запустить" во вкладке "Веб"
      настроек (`app/web_server.py`, `app/settings_dialog.py`). Автозапуска
      вместе с приложением нет и не планировалось — только порт как
      предпочтение (`settings["web_port"]`) сохраняется между сессиями,
      само включение — нет

**Архитектура backend** (`web/backend/`, Rust, зависит от `cove-core`
напрямую, без FFI — ARCHITECTURE.md §1): один процесс обслуживает один
`.slr`-контейнер. `Container` никогда не живёт в общем состоянии сервера —
при успешном `/api/login` он передаётся во владение выделенному
ОС-потоку-актору (`actor.rs`, не в пул tokio), HTTP-хендлеры общаются с ним
только через `std::sync::mpsc` + `oneshot`-ответы (ARCHITECTURE.md §4).
Сессии живут в памяти процесса (`state.rs`), протухают через 30 минут
бездействия (лениво проверяется при каждом запросе). Core для этого
понадобился один новый метод — `import_file_from_bytes()` (загрузка из
multipart, а не с локального пути на диске).

Маршруты: `/api/login`, `/api/logout`, `/api/me`, `/api/library`,
`/api/trash`, `/api/search`, `/api/folders`, `/api/upload` (multipart),
`/api/files/{id}/download` (с поддержкой `Range` — нужно для перемотки
видео/аудио в браузере), `/api/files/{id}` (`DELETE`), `/restore`,
`/rename`, `/move`, `/favorite`. Все, кроме health/login, проверены вручную
через curl на живом инстансе: логин, неверный пароль → 401, запрос без
CSRF-токена → 403, создание папки, загрузка, полное и частичное (`Range`)
скачивание, переименование, избранное, поиск, удаление/корзина,
логаут → сессия действительно инвалидируется, брутфорс → 429 на 11-й
попытке.

**Фронтенд** (`web/frontend/`) — vanilla HTML/CSS/JS без сборки, отдаётся
тем же Axum-сервером как статика (`ServeDir` fallback). ARCHITECTURE.md
изначально набрасывал Svelte/TS — сознательно отклонились от этого для
MVP: объём UI не оправдывает npm/vite build tooling, а API не завязан на
конкретный фронтенд, так что вернуться к Svelte позже можно без изменений
backend. Экран входа, библиотека с папками/хлебными крошками, избранное,
корзина, поиск, загрузка (drag через `<input type=file multiple>`),
скачивание/просмотр по клику. При тестировании обнаружилось, что
`window.prompt()` в некоторых окружениях (в частности, автоматизированный
браузер, использованный для проверки) молча отклоняется без открытия
диалога — заменено на собственное лёгкое модальное окно
(`showPrompt()` в `app.js`), что и надёжнее для тестирования, и не
блокирует вкладку целиком, как это делают нативные диалоги.

**Известное ограничение, не решённое в этой фазе**: Core пока не делает
file-level advisory locking (flock) над `.slr`-файлом. Если открыть одно и
то же хранилище одновременно в десктопе и через веб-сервер и
редактировать в обоих местах, более поздний commit молча перезапишет
более ранний — классическая проблема нескольких писателей без
координации. Это не проглядели: явное предупреждение есть в UI вкладки
"Веб" настроек. Настоящее исправление — межпроцессная блокировка в
`Container::create`/`open` — самостоятельная по объёму задача (новый
вариант `CoveError`, изменения во всех биндингах под него), сознательно
вынесена за рамки Фазы 13.

Также: `/api/files/{id}/download` без заголовка `Range` отклоняет файлы
больше 4 ГиБ (`u32::MAX`) с понятной ошибкой вместо тихого обрезания —
`Container::read_at()` принимает `len: u32`, это уже существующее
ограничение Core API, не новое. Со `Range`-запросами (как их шлёт
video/audio-плеер браузера) ограничения нет, т.к. каждый запрос читает
ограниченный кусок.

**Интеграция с десктопом**: `MainWindow` теперь получает путь к
открытому файлу контейнера (раньше нигде не сохранялся — только
расшифрованный `Container` прокидывался в `_on_unlocked`) и владеет
`WebServerManager` (`app/web_server.py`) — тонкой обёрткой над
`subprocess.Popen` вокруг бинарника `cove-web-backend`. Сервер
останавливается при логауте и при закрытии окна (`closeEvent`), чтобы не
оставлять процесс-сирота. Проверено офскрин Qt-тестом, который реально
запускает подпроцесс и проверяет живой HTTPS-ответ `/health`, а не только
состояние виджетов.

репозиториях его нет; `rustup` — тоже через pacman, отдельным набором
Android-таргетов (`aarch64-linux-android`, `armv7-linux-androideabi`,
`x86_64-linux-android`, `i686-linux-android`), не трогая системный
pacman-`rustc`, который остаётся дефолтным для всего остального workspace
(нюанс: пакет `rustup` на Arch сам подменяет `/usr/bin/cargo`/`rustc`
symlink'ами на себя — пришлось дополнительно поставить `rustup component
add clippy rustfmt`, иначе `cargo clippy --workspace` ломался бы для ВСЕХ
крейтов, не только android). Линковка — через `.cargo/config.toml` в корне
репозитория (не в `bindings/android/` — cargo ищет `.cargo/config.toml` от
текущей рабочей директории вверх, а не от манифеста крейта) с explicit
`CC_*`/`AR_*` под каждый таргет (`blake3` компилирует NEON-путь на C и не
находит версионированные NDK-компиляторы (`aarch64-linux-android24-clang`)
без этого). minSdk = 24 — выбор без переписки, привязан к тому, под какую
версию слинкованы `.so`.

**UniFFI-слой** (`bindings/android/src/lib.rs`) — 1:1 зеркало PyO3-биндингов
(`Container`/`LockedContainer`, все файловые операции, пользователи,
поиск, избранное, миниатюры, журнал входов), в proc-macro режиме (без
`.udl`). Отличия от PyO3, потребовавшие реальных решений, а не просто
трансляции:
- UniFFI Object-типы (`AndroidContainer`) раздаются Kotlin-стороне как
  `Arc<Self>` и вызываются из корутин, а не эксклюзивно из одного потока —
  пришлось обернуть `Container` в `Mutex<Option<_>>` вместо голого
  `Option<_>`, как в PyO3 (там за эксклюзивность отвечает GIL).
- UniFFI не поддерживает голые Rust-кортежи через границу — `(String,
  Role)` из `list_users()` пришлось завернуть в отдельный `Record`
  (`UserEntry`), которого нет в PyO3-версии.
- Метод `close()` конфликтовал с `close()`/`AutoCloseable`, которые UniFFI
  сам генерирует для Object-типов (реальная ошибка компиляции Kotlin,
  "Conflicting overloads") — переименован в `close_container()`.
- Ошибки — свой `AndroidError` (`#[derive(uniffi::Error)] #[uniffi(flat_error)]`)
  с тем же маппингом категорий, что и PyO3/Web (ARCHITECTURE.md §3): наружу
  уходит категория, не детали.

Собран и провалидирован под все 4 ABI (`aarch64`/`armv7`/`x86_64`/`i686`,
`file` подтверждает NDK r27d/API24), Kotlin-биндинги генерируются через
отдельный `uniffi-bindgen` bin-таргет. `scripts/build_android_bindings.sh`
автоматизирует весь цикл (сборка → генерация Kotlin → раскладка `.so` по
`jniLibs/<abi>` и `.kt` в исходники приложения) — аналог
`build_python_bindings.sh` для desktop.

**Каркас приложения** (`android/`) — Gradle-проект (AGP 8.7.3, Kotlin 2.1,
отдельный Compose Compiler plugin — с Kotlin 2.x он больше не встроен в
основной Kotlin-плагин), Jetpack Compose, `MainActivity` пока показывает
только `coreVersion()` — это сквозная проверка, что JNA грузит `.so` и
реально вызывает Rust, а не заглушка. `android:allowBackup="false"` в
манифесте — осознанно, чтобы Android Auto Backup не пытался сам решить,
можно ли резервировать зашифрованный контейнер/обёртку ключа в облако.

**Реальные проблемы, найденные при сборке и запуске на эмуляторе (не
гипотетические)**:
1. `compileSdk = 36` (SDK Platform на машине — превью-версия с
   `AndroidVersion.ApiLevel=36.1`) потребовал новее build-tools, которые
   Gradle сам докачал через встроенный установщик при первом билде.
2. `android.useAndroidX=true` в `gradle.properties` — без него любая
   AndroidX-зависимость валит сборку с понятной ошибкой (это просто
   обязательный флаг, не баг, но лёгкий шаг легко забыть).
3. **16KB page size**: Google Play с конца 2025 требует от новых
   приложений совместимости с устройствами с 16KB (не 4KB) page size, и
   локальный эмулятор (Pixel-образ из SDK) уже такой. Собранный
   `libcove_core_uniffi.so` изначально линковался под старое 4KB-
   выравнивание ELF-сегментов — система показывала `PageSizeMismatchDialog`
   при живом запуске на эмуляторе. Исправлено `-C link-arg=-Wl,-z,max-page-size=16384`
   в `rustflags` для всех 4 android-таргетов в `.cargo/config.toml`.
   Отдельно всплыла **та же** проблема в стороннем `net.java.dev.jna:jna:5.15.0`
   (его `libjnidispatch.so` был выровнен под 4KB) — обновление до `5.17.0`
   её решило. Это была бы совершенно невидимая проблема без реального
   запуска на эмуляторе — юнит-тесты/просто успешная компиляция её никак
   не поймали бы, только `readelf`/живой запуск и системный диалог.

Проверено по-настоящему: `cargo build`/`clippy` под все 4 таргета и host,
`gradle assembleDebug` → `adb install` → `adb shell am start` → скриншот
реального экрана эмулятора с текстом `cove-core 0.1.0`, пришедшим из Rust
через JNA, без предупреждений в logcat.

**Экраны** (`android/app/src/main/kotlin/com/cove/app/screens/`) — простая
sealed-навигация без Navigation-Compose (объём экранов не оправдывает
роутер сейчас): `WelcomeScreen` → `CreateContainerScreen` (с реальным
Argon2id-хэшированием через `withContext(Dispatchers.IO)`, чтобы не
блокировать UI-поток) → `RecoveryPhraseScreen` (BIP39-фраза показывается
ровно один раз, как в desktop) → `LibraryScreen` (список папок/файлов,
создание папки, удаление, избранное, breadcrumb-навигация). `LoginScreen`
повторяет то же UX-решение, что и в desktop (username+password напрямую,
без выбора файла) — при наличии "основного" хранилища (сохраняется в
`ContainerRegistry`, обёртка над `SharedPreferences`) экран входа
открывается сразу, минуя приветствие.

На Android хранилища физически живут в app-private storage
(`filesDir/containers/*.slr`), а не там, где укажет пользователь — прямого
доступа к произвольным путям файловой системы нет (Scoped Storage), только
через SAF-импорт, который является отдельной задачей ниже.

**Реальный краш, найденный только благодаря честному end-to-end тестированию
через adb (не просто сборкой)**: при первом же создании папки в непустой
`LazyColumn` приложение падало с `java.lang.IllegalArgumentException: Type
of the key 1 is not supported. On Android you can only use types which can
be stored inside the Bundle.` — `items(entries, key = { it.fileId })`
использовал Kotlin `ULong` в качестве ключа, а `LazyColumn`'s `key`
обязан быть Bundle-совместимым типом (для saveable state), которым `ULong`
не является. `cargo build`/`gradle assembleDebug` это не ловят — только
реальный запуск с непустым списком. Исправлено `it.fileId.toLong()`.
Диагностика заняла несколько итераций: сначала списывалось на промахи
координат `adb shell input tap` (ADB Gboard-тулбар и Compose-диалоги дают
неочевидные bounds на глаз), но `uiautomator dump` дважды подтвердил
точное попадание в кнопку "Создать" — и только `adb logcat` вскрыл
настоящую причину (`FATAL EXCEPTION`, а не промах). После фикса —
создание/навигация/удаление папки, повторный логин с сохранёнными
учётными данными и logout проверены живьём на эмуляторе от начала до
конца.

**Android Keystore + биометрия** (`android/app/src/main/kotlin/com/cove/app/security/BiometricVault.kt`)
— биометрия НЕ хранит DEK/KEK контейнера напрямую: Core принимает только
username+password для `unlock()`, так что под замком лежит сам пароль
пользователя, зашифрованный AES-ключом из `AndroidKeyStore` с
`setUserAuthenticationRequired(true)` + `setInvalidatedByBiometricEnrollment(true)`
(ключ физически не отдаёт содержимое без свежего прохождения биометрии на
аппаратном уровне; при регистрации нового отпечатка на устройстве старый
ключ автоматически становится недействителен — код это ловит через
`KeyPermanentlyInvalidatedException` и просто просит войти паролем заново
вместо падения). Зашифрованный blob дополнительно лежит в
`EncryptedSharedPreferences` (defense in depth, не единственная линия
защиты). После первого успешного входа паролем — если биометрия доступна
на устройстве и ещё не включена для этого хранилища — предлагается
включить её; кнопка "Войти по биометрии" на экране входа появляется только
когда для конкретного пути и то и другое верно (`isBiometricAvailable()` +
`hasSavedCredentials(path)`).

**Три реальных бага, найденных только благодаря живому end-to-end
тестированию на эмуляторе с настоящим PIN-кодом и настоящим
зарегистрированным виртуальным отпечатком** (`adb emu finger touch`) — ни
один не всплыл бы при простой сборке:
1. **Data loss при выходе**: `create_folder`/`delete_file` и подобные
   операции в Core только мутируют File Table в памяти — реальный commit
   на диск происходит в `close()` (проверено чтением `core/src/container/mod.rs`).
   Обработчик "Выход" запускал `closeContainer()` в фоновой корутине, не
   дожидаясь её, и сразу переключал экран — если процесс убивался раньше,
   чем корутина успевала завершиться, несохранённые изменения терялись.
   Поймано вживую: удалённая папка "вернулась" после переустановки APK.
   Исправлено — экран теперь дожидается `closeContainer()` перед сменой
   состояния навигации. (Более широкий риск — потеря данных при уходе из
   приложения без явного "Выход", например системный swipe-away — не решён,
   потребует lifecycle-хука на `onStop`, это отдельная задача.)
2. **Диалог "включить биометрию?" никогда не показывался**: `onUnlocked()`
   вызывался сразу после успешной разблокировки, из-за чего экран входа
   мгновенно сменялся на библиотеку раньше, чем `AlertDialog` успевал
   отрендериться. Исправлено — контейнер придерживается в `pendingContainer`,
   `onUnlocked()` вызывается только после того, как пользователь ответит
   на диалог (в любую сторону).
3. **`IllegalBlockSizeException` при первом включении биометрии**: ключ с
   `setUserAuthenticationRequired(true)` требует свежую аутентификацию не
   только на расшифровку, но и на само шифрование — `enroll()` пытался
   зашифровать пароль сразу после генерации ключа, без прохождения
   `BiometricPrompt`, и Keystore закономерно отклонял операцию. Исправлено
   — `enroll()` тоже показывает `BiometricPrompt` с `CryptoObject(cipher)`
   и шифрует только после `onAuthenticationSucceeded`.

Проверено по-настоящему, не только сборкой: `adb shell locksettings set-pin`
+ полный проход экрана регистрации отпечатка в Settings + `adb emu finger
touch` — enroll (пароль реально шифруется через Keystore после
прохождения `BiometricPrompt`) → logout → повторный вход **только
касанием сенсора**, без ввода пароля → реальная расшифровка → реальный
`unlock()` → библиотека с ранее созданной папкой.

**Scoped Storage / SAF** (`android/app/src/main/kotlin/com/cove/app/screens/LibraryScreen.kt`)
— на Android (API 29+) нет прямого доступа к произвольным путям файловой
системы, только через `content://`-URI, которые выдаёт система после
выбора файла пользователем. Импорт — `ActivityResultContracts.GetContent()`
открывает системный пикер, оригинальное имя файла достаётся через
cursor-запрос колонки `OpenableColumns.DISPLAY_NAME` (у content-URI обычно
нет осмысленного пути), байты читаются через
`contentResolver.openInputStream(uri)` и идут в уже существующий
`Container::import_file_from_bytes()` (добавлен в Core ещё в Фазе 13 для
web-загрузок — пригодился здесь без изменений). Экспорт —
`ActivityResultContracts.CreateDocument("*/*")` даёт URI для записи в
любое место, которое выберет пользователь (Downloads, Google Drive и
т.п.); файл читается целиком одним `readAt()` — тот же осознанный
компромисс MVP, что и в `web/backend` (без Range нет смысла для
локального экспорта, тот же документированный лимит на очень большие
файлы).

Иконки на кнопках импорта/экспорта — простые Unicode-символы (⬆/⬇), не
`material-icons-extended`: эта библиотека тянет тысячи иконок ради двух
штук, которых нет в уже подключённом `material-icons-core` — неоправданно
тяжёлая зависимость для этого объёма UI.

Проверено по-настоящему на эмуляторе: реальный файл записан через `adb
push` в `/sdcard/Download/`, импортирован через настоящий системный
пикер (навигация Recent → Downloads → выбор файла), появился в
библиотеке с точным размером (32 Б, совпадает с оригиналом) → экспортирован
через `CreateDocument` (системный диалог "Save as" с предзаполненным
именем) → итоговый файл на устройстве прочитан через `adb shell cat` и
побайтово совпал с исходным содержимым. Полный round-trip
импорт→шифрование→хранение→расшифровка→экспорт подтверждён без потери
данных.

**Фаза 14 (Android) закрыта целиком**: toolchain, UniFFI-слой, каркас
приложения, экраны (приветствие/создание/вход/библиотека), Android
Keystore + биометрия, Scoped Storage/SAF — всё реализовано и проверено
вживую на эмуляторе, не только сборкой. По пути найдено и исправлено
четыре реальных бага (два в этой фазе — крэш `LazyColumn` с `ULong`-ключом
и потеря данных при `logout` — и два в биометрии — незапускавшийся диалог
и `IllegalBlockSizeException`), что подтверждает ценность именно живого
end-to-end тестирования поверх одной успешной компиляции.

**UX-доработка после первой прогонки** (по прямому запросу — интерфейс
библиотеки было неудобно использовать без разделов и с двумя мелкими

Библиотека/Фото/Видео/Документы/Музыка/Избранное — те же виртуальные

(`storage/AppSettings.kt` — тема Системная/Светлая/Тёмная, применяется

плюс "забыть биометрию для этого хранилища" через уже существующий

Проверено вживую: переключение разделов через drawer, виртуальный раздел
"Документы" через реальный `search()` с файлом, добавленным через SAF,
раскрывающееся FAB-меню, переключение темы (применяется мгновенно, без
перезапуска). По пути — честно задокументированный не-баг: тестовый файл
не находился в разделе "Документы", потому что при повторном тестировании
SAF был по ошибке импортирован файл с именем `saf_test.txt (1)`
(суффикс от предыдущего экспорта, добавленный самим системным пикером) —
`categorize()` в Core берёт расширение как всё после последней точки, а
не что-то со смыслом уровня MIME-типа, так что `"txt (1)"` не совпадал с
`"document"`. Это не баг Cove — так же вело бы себя большинство простых
классификаторов по расширению; отмечено на будущее как штрих к тестовым
сценариям, не как задача на исправление.

**UX-доработка, второй раунд** (по прямому запросу — FAB был слишком
крупным, меню при открытии выглядело узким и уезжало не в ту сторону,
а кнопка добавления файлов отсутствовала вне корня библиотеки):
`LargeFloatingActionButton` заменён на обычный `FloatingActionButton`
(заметно компактнее); `DropdownMenu` теперь открывается с `shape =
RoundedCornerShape(20.dp)`, `modifier = Modifier.widthIn(min = 220.dp)`
и `offset = DpOffset(x = 0.dp, y = (-16).dp)` — раскрывается вверх от
кнопки, с правыми гранями меню и кнопки на одной вертикальной линии, и не
выглядит узким; текст пунктов меню — `MaterialTheme.typography.titleMedium`
вместо стандартного (крупнее). (Смещение подбиралось в два захода по
отзывам после проверки на эмуляторе: сначала `(-176, -128)` — меню
визуально отрывалось от кнопки в сторону; затем `(-56, -16)` — всё ещё не

desktop он есть в `SECTIONS`, пользователю об этом расхождении сказано
прямо).

Проверено вживую на эмуляторе: скриншоты подтвердили и уменьшенный размер
FAB, и раскрытие меню вверх-влево со скруглёнными углами и увеличенным
текстом; переход в раздел "Фото" через drawer показал кнопку "+" там, где
раньше её не было; список разделов в drawer подтверждён без "Музыки"
(Библиотека/Фото/Видео/Документы/Избранное + Настройки).

устройствами (без облака — например, по Wi-Fi/локальной сети) упомянута

**Найденный и закрытый пробел — превью и просмотрщики файлов на Android
отсутствовали.** Пользователь заметил вживую: тап по фото ничего не делал,
миниатюр в списке не было. Причина — десктопные Фаза 7 (просмотрщики) и
Фаза 8 (миниатюры) при переносе на Android в Фазе 14 не были портированы:
строка списка была кликабельна только для папок (`clickable(enabled =
entry.isFolder, ...)`), Core/UniFFI при этом уже полностью предоставлял
всё нужное (`readAt`, `thumbnail`, `findThumbnail`) — не хватало только
Kotlin-слоя. Реализовано:

- `media/FileKind.kt` — та же классификация по расширению, что и в
  desktop `file_kind.py`.
- `media/Thumbnails.kt` — генерация PNG-миниатюр (`BitmapFactory` +
  `Bitmap.createScaledBitmap`, 160px по большей стороне — тот же размер,
  что и `desktop/app/thumbnails.py`), показ в `FileRow` с кэшем в памяти
  на время сессии экрана.
- `screens/ImageViewerScreen.kt` — полноэкранный просмотр, `readAt()`
  файла целиком + decode, без временных файлов на диске.
- `screens/TextViewerScreen.kt` — то же для .txt/.md (UTF-8 decode).
- `media/ContainerDataSource.kt` + `screens/MediaViewerScreen.kt` —
  видео/аудио через media3 ExoPlayer поверх кастомного `DataSource`,
  стримящего байты через `container.readAt()` по требованию — Android-
  аналог desktop `ContainerFileDevice` (Фаза 7): ни один temp-файл с
  расшифрованным видео на диске не создаётся.
- `media/ExternalOpen.kt` — для типов без встроенного просмотрщика (pdf,
  RAW и т.п.) честный диалог "открыть во внешнем приложении?" (как
  desktop `_open_unsupported`), а не молчаливый тап. Экспорт — в
  `cacheDir/exports`, отдаётся другому приложению только через
  `FileProvider`/`content://` с разовым правом на чтение (добавлен
  `<provider>` в `AndroidManifest.xml` + `res/xml/file_paths.xml`).

Проверено вживую на эмуляторе, реальными файлами (не заглушками): PNG
(настоящий скриншот) — миниатюра появилась в списке, полноэкранный
просмотр показал точное содержимое; MP4 (сгенерирован `ffmpeg`,
SMPTE-цветные полосы + тон 440Гц) — воспроизвёлся от начала до конца
через `ContainerDataSource`; TXT с кириллицей — текст воспроизведён
точно, включая юникод; "pdf" (256 случайных байт, намеренно невалидный) —
диалог честно предложил открыть во внешнем приложении, экспорт через
`FileProvider` отработал, система направила его в Google Диск (обработчик
по MIME `application/pdf`), тот корректно сообщил "invalid format" — то
есть весь путь до сторонего приложения подтверждён, файл дошёл
побайтово, ошибка ожидаема (тестовый файл и должен быть невалиден).

## Фаза 15. Оптимизация

- [x] Многопоточность (Rust: `rayon`/`tokio` где уместно)
- [x] Кэш метаданных в памяти, быстрое открытие контейнера
- [x] Профилирование на коллекциях 100k+ файлов

Подход: сначала реальный бенчмарк на большой библиотеке
(`core/examples/large_library_bench.rs` — `cargo run --release --example
large_library_bench -- <N>`, печатает тайминги импорта/close/unlock/
list_dir/search), затем — оптимизация того, что бенчмарк реально показал
узким местом, а не того, что казалось узким местом заранее. Это тот же
принцип, что уже был задокументирован в `search.rs` при выборе in-memory
скана вместо персистентного индекса в Фазе 9 — Фаза 15 его проверяет на
практике, а не постулирует.

**Baseline на 100 000 файлах** (до изменений): импорт 100k файлов — 39.0s
(0.39ms/файл), `close()` — 0.026s, повторное открытие (`unlock`, включая
decode File Table) — 0.054s, `list_dir(root)` — 0.015s, `search()` — 0.028s.

Неожиданный результат: `close()`/`unlock()`/`list_dir()`/`search()` уже
были быстрыми на 100k записей без каких-либо изменений — резидентный
`Vec<FileEntry>` в памяти справляется, ровно как предсказывал комментарий
в `search.rs`. Узким местом оказался **импорт**, а не открытие контейнера.

Расследование импорта показало две причины, и только одна из них
подтвердилась:
- **Гипотеза №1 (не подтвердилась)**: `fsync` на каждый импортируемый файл
  в `write_blocks_from_reader`. Убран — он и не давал реальной гарантии
  сохранности (блоки без записи в File Table недостижимы до `close()`,
  который сам делает fsync), но замер до/после (39.0s → 42.5s, в пределах
  шума) показал, что дело не в нём. Изменение всё равно оставлено — оно
  корректно и чуть дешевле, просто не было причиной торможения.
- **Гипотеза №2 (подтвердилась)**: `next_file_id()` делал **линейный скан
  всей `file_table`** (`.iter().map(...).max()`) на каждый импортируемый
  файл — O(n) на вызов, O(n²) суммарно на массовом импорте. При росте N
  время на файл росло (0.295мс → 0.308 → 0.334 → 0.425мс при 10k → 20k →
  40k → 100k файлов) — характерный признак квадратичного роста. Заменено
  на кэшированный счётчик `next_file_id: FileId` в `Container` (инициализируется
  из `max(file_table)+1` при `unlock`, из `1` при `create`, инкрементируется
  за O(1)) — классический "кэш метаданных в памяти" из формулировки этой
  фазы, только не для File Table целиком (она и так уже была кэширована),
  а для производного значения, которое неправильно пересчитывалось заново.

**После исправления**: импорт 100k файлов — 27.0s (0.270ms/файл, кроме
того теперь стабильно линейно: 0.272 → 0.282 → 0.270мс/файл на 10k / 40k /
100k — квадратичный рост исчез). На 300k файлах: импорт 82.8s
(0.276ms/файл — линейность подтверждена и на большем объёме), `close()` —
0.095s, `unlock()` — 0.120s, `list_dir` — 0.073s, `search()` — 0.105s — всё
по-прежнему на уровне долей секунды.

**Многопоточность**: страницы File Table (по `MAX_ENTRIES_PER_PAGE=4096`
записей) уже были независимыми AEAD-блоками (свой nonce на страницу) —
`encode_file_table`/`decode_file_table` в `format/file_table.rs`
распараллелены по страницам через `rayon` (`par_iter`/`par_iter().map()`),
формат на диске не изменился. На измеренных объёмах (100k–300k записей,
25-75 страниц) эффект в абсолютных цифрах небольшой, потому что
однопоточный вариант и так укладывался в десятки миллисекунд — но рост
теперь размазан по ядрам, а не всё на одном, что имеет значение на
слабых Android-устройствах и при больших объёмах, для которых считался
бенчмарк.

**Осознанно не сделано — ленивая (постраничная) загрузка File Table /
персистентный индекс поиска** (`Superblock.search_index_offset/len` всё
ещё зарезервированы, но не используются, как и раньше). Причина —
измеренная, а не предполагаемая: `unlock()`/`search()`/`list_dir()`
остаются быстрыми (сотни миллисекунд даже на 300k записей) при полностью
резидентной `file_table`, так что перестройка на ленивую подгрузку
страниц с индексом по `parent_id`/категориям добавила бы существенную
сложность (нужен настоящий индекс, а не просто offset-резервация) без
измеримой пользы на реалистичных объёмах библиотеки. Возвращаться к этому
имеет смысл, если реальное использование когда-нибудь упрётся в объёмы,
на которых резидентный `Vec<FileEntry>` перестанет помещаться в память
разумного размера (десятки миллионов записей) — не раньше.

Пересобраны и обновлены оба набора биндингов, чтобы приложения реально
получили эффект: `desktop/cove_core_py.so`
(`scripts/build_python_bindings.sh`) и Android `.so`/Kotlin-биндинги
(`scripts/build_android_bindings.sh`). Публичный API Core не менялся —
все изменения (счётчик `next_file_id`, распараллеливание File Table,
удаление избыточного `fsync`) внутренние, поэтому существующие 56
unit/integration-тестов Core прошли без изменений.

## Фаза 16. Сборка

- [x] Windows, Linux, Android — сборка через CI
- [x] Подпись релизов (APK signing на Android; Windows code signing — сознательно отложено, см. ниже)
- [x] Автоматическая сборка по тегам версий

**Git-репозиторий**: до этой фазы проект вообще не был под git (несмотря
на то, что `.github/workflows/ci.yml` существовал с Фазы 1 — он ни разу
реально не запускался на GitHub, пушить было некуда). Инициализирован
`git init` локально, добавлен `.gitignore` (build-артефакты Android/
Gradle, `*.slr`-контейнеры, `.claude/settings.local.json`, keystore-файлы
и т.д.), сделан первый коммит текущего состояния. GitHub-remote и push —
осознанно не сделаны в рамках этой фазы, это отдельное действие с
видимыми внешними последствиями, которое должно быть явным решением
пользователя, а не побочным эффектом настройки CI.

**Android — реальная подпись release-сборки**: сгенерирован настоящий
release-keystore (`keytool`, RSA 4096, самоподписанный сертификат
валиден до 2056 — с большим запасом сверх минимума Google Play в 2033).
`android/app/build.gradle.kts` читает `android/keystore.properties`
(не в git, см. `.example`-шаблон) и настраивает `signingConfigs.release`;
без файла release-сборка компилируется, но остаётся неподписанной — не
падает, чтобы не ломать обычные CI-джобы, которым release не нужен.
Проверено вживую: `assembleRelease` → `apksigner verify` подтвердил
подпись (SHA-256 отпечаток совпадает с ключом) → APK установлен на
эмулятор поверх debug-версии (потребовалась переустановка — Android не
позволяет держать разные подписи под одним `applicationId`) → создано
настоящее хранилище через реальный Core (Argon2 + BIP39) — сгенерирована
настоящая фраза восстановления, значит нативная библиотека в
release-сборке (без минификации, `isMinifyEnabled=false`) работает
корректно, а не просто "собирается". Для Android APK самоподписанный
keystore — это штатный, а не временный способ подписи (в отличие от
Windows, ниже) — Google Play принимает любой ключ, который сам
разработчик генерирует и хранит; критично только не потерять его,
иначе обновления того же приложения станут невозможны.

**Windows code signing — сознательно не сделано.** Требует настоящего
сертификата от удостоверяющего центра (стоит денег, процедура
верификации организации/личности) — self-signed сертификат не даёт
Windows SmartScreen никакого доверия, то есть был бы имитацией, а не
реальной подписью. `release.yml` собирает Windows-версию (PyInstaller,
`.exe`) без подписи и явно помечает артефакт как `cove-windows-unsigned`.
Когда сертификат появится, шаг `signtool sign` добавляется в
`windows-desktop` job тем же паттерном, что и Android (секреты через
GitHub Secrets, cert в base64).

**Desktop-упаковка (PyInstaller)**: `desktop/cove.spec` — один
исполняемый файл, явно подключает `cove_core_py.so`/`.pyd` (платформенно
верное имя определяется в самом spec-файле, `.so` на Linux/macOS, `.pyd`
на Windows — иначе Windows-сборка тихо не находила бы файл, эта нестыковка
поймана до реального прогона в CI, не после). На Linux собрано и реально
запущено (`QT_QPA_PLATFORM=offscreen`, процесс стартовал и работал без
падений) — 106MB standalone ELF-бинарник, PySide6 + Rust-биндинги внутри.
Windows-сборка в CI написана по тем же принципам (переименование `.dll`
→ `.pyd`, тот же `.spec`), но **не проверена вживую** — на этой машине нет
Windows, поэтому корректность `windows-desktop` job в `release.yml`
подтверждена только синтаксическим/логическим разбором, не реальным
прогоном. Единственное реально пойманное несоответствие (расширение
`.so` было захардкожено в первой версии `cove.spec`, что сломало бы
именно Windows-сборку) — иллюстрация того, зачем вообще стоило прописать
эту логику явно, а не полагаться на предположения о переносимости.

**Linux AppImage** (по прямому запросу — "упрощённый запуск для Linux"):
`scripts/build_appimage.sh` поверх уже существующего `cove.spec` — берёт
готовый PyInstaller onefile-бинарник, кладёт в `AppDir/usr/bin/Cove`,
добавляет `.desktop`-файл и иконку (`desktop/packaging/cove.svg` —
простой плейсхолдер "C" в круге в акцентном синем цвете desktop-темы
`#0a84ff`, тем же духом временности, что и Android-плейсхолдер из Фазы
14 — реальный дизайн иконки отдельная непрограммистская задача),
рендерит её в PNG через `rsvg-convert` прямо в момент сборки (не
коммитится растровый файл — только SVG-первоисточник). Собирает сам
AppImage через официальный `appimagetool` (скачивается скриптом при
отсутствии, тот же принцип, что и с NDK в CI). Результат — один файл
`Cove-x86_64.AppImage`, ~106МБ, запускается без ручной установки Python/
PySide6/venv. Проверено вживую дважды: через `--appimage-extract-and-run`
(на случай отсутствия FUSE) и через обычный прямой запуск с реальным
FUSE-монтированием (`/tmp/.mount_Cove-*`) — оба раза процесс стартовал,
работал и завершался штатно. Подключено в `release.yml` (`linux-desktop`
job) — публикуется в GitHub Release вторым артефактом рядом с голым
бинарником.

**CI/CD**: новый `.github/workflows/release.yml` (тег `v*.*.*` или
`workflow_dispatch`) — три параллельные джобы (`linux-desktop`,
`windows-desktop`, `android`) собирают артефакты, `publish-release`
публикует их в GitHub Release (только при пуше тега, не при ручном
запуске). Существующий `.github/workflows/ci.yml` не тронут — он остаётся
быстрой проверкой на каждый push/PR (тесты + architecture-boundary +
кросс-компиляция Core под Android через `cargo-ndk`), а `release.yml` —
более тяжёлая, редко запускаемая сборка реальных дистрибутивов. Android-
джоба качает тот же NDK r27d, что стоит локально (в `/opt/android-ndk` —
путь, захардкоженный в `.cargo/config.toml` с Фазы 14), вместо того чтобы
переписывать этот уже проверенный локальный конфиг ради переносимости.
Добавлен Gradle wrapper (`android/gradlew`, ранее отсутствовал — сборка
держалась на системном Gradle 9.6.1), без него `release.yml` не мог бы
воспроизводимо собирать Android на чужой машине/раннере.

**Не проверено вживую** (честно, а не молча): весь `release.yml`
целиком — реальный прогон на GitHub Actions runner'ах (нет push в
GitHub-remote в рамках этой фазы); Android-джоба в CI полагается на
`ANDROID_SDK_ROOT`, который на GitHub-hosted ubuntu-latest раннерах
обычно предустановлен — это распространённая практика, но не
верифицированная лично в этом окружении. Публикация в GitHub Release
требует реального `ANDROID_KEYSTORE_BASE64`/`ANDROID_KEYSTORE_PASSWORD`/
`ANDROID_KEY_ALIAS`/`ANDROID_KEY_PASSWORD` секретов в настройках
репозитория (значения — из локального `android/keystore.properties`,
`storeFile` кодируется в base64: `base64 -w0 android/release.keystore`) —
это тоже должен сделать сам пользователь, не то, что можно настроить
без доступа к GitHub UI/токену репозитория.

## Фаза 17. Тестирование

```
Создание контейнера → добавление файлов → просмотр → поиск → web → Android
   → большие файлы → 100000+ файлов → повреждение контейнера → восстановление
```

- [x] Unit/integration тесты Core (Rust)
- [x] **Fuzzing парсера `.slr`** — повреждённый/злонамеренный файл не должен
      приводить к падению с возможностью эксплуатации
- [x] Тест на устойчивость к сбоям: `kill -9` посреди записи, контейнер
      должен остаться открываемым (см. атомарность в Фазе 2)
- [x] Нагрузочное тестирование на больших коллекциях и больших файлах

**Аудит существующего покрытия**: до этой фазы уже было 56 unit-тестов
(roundtrip + ручные corruption-тесты на каждый format-модуль). Хорошая
база, но написанная вручную — покрывает то, что придумал разработчик, а
не то, что нашёл бы автоматический перебор. Это и стало причиной перейти
к настоящему fuzzing вместо того, чтобы просто дописать ещё unit-тестов.

**Fuzzing нашёл 3 реальных уязвимости** (не гипотетических — конкретные,
воспроизводимые, с рабочим PoC) вручную при разборе кода парсера перед
тем, как писать fuzz-таргеты, и подтверждены ~40 миллионами прогонов
`cargo fuzz` (`core/fuzz/`, 4 таргета — header/keyslots/commit_pointer/
file_table, по 30с на таргет, ни одного нового краша сверху найденного
руками). Общий паттерн у всех трёх: значение длины/счётчика, лежащее
**до** или **вне** AEAD-аутентификации, использовалось напрямую как размер
аллокации — специально сфабрикованный (не просто случайно повреждённый)
`.slr`-файл мог заставить процесс попытаться выделить гигабайты памяти и
упасть OOM-абортом:

1. `LockedContainer::open()` — `header.keyslots_len` (plaintext header, за
   пределами какой-либо аутентификации помимо самосогласованного
   checksum'а, который атакующий волен пересчитать под любое значение)
   использовался как размер `vec![0u8; ...]` напрямую. Исправлено:
   сверяется с единственно верной константой (`SLOT_LEN * CAPACITY`) до
   аллокации.
2. `Container::read_block_at()` — `plaintext_len` из заголовка блока
   данных (лежит перед AEAD-шифртекстом, им не защищён) использовался как
   размер аллокации до расшифровки. Легитимный блок никогда не превышает
   `block_size` — исправлено сверкой перед аллокацией.
3. `file_table::decode_file_table()` — `page_count`, framing вокруг
   AEAD-страниц (не их содержимое), не защищён. Исправлено: заявленное
   число страниц физически не может превышать `bytes.len() / 4`
   (минимум 4 байта на страницу под её же префикс длины) — проверяется
   до `Vec::with_capacity`.

Важно честно отметить: все три бага требуют доступа на **запись** к
файлу-контейнеру без пароля (например, evil maid со сворованным
диском/бэкапом) — они не позволяют прочитать зашифрованные данные без
пароля, "только" обрушивают процесс честного пользователя при следующей
попытке открыть свой же (испорченный кем-то другим) контейнер. Это
denial-of-service, не утечка plaintext — но именно такой класс багов
явно назван в этом пункте ROADMAP ("злонамеренный файл не должен
приводить к падению"), поэтому исправлен. Похожие места
(`free_map`/`login_log`/поштучный `count` внутри `file_table`-страницы)
проверены и оказались безопасны — их длины читаются уже ИЗ
расшифрованного (успешно аутентифицированного AEAD) plaintext, то есть
недоступны атакующему без пароля. Добавлены три регрессионных теста
(`forged_huge_keyslots_len_rejected_not_oom`,
`forged_huge_block_plaintext_len_rejected_not_oom`,
`forged_huge_page_count_rejected_not_oom`) — 59 unit-тестов итого.

**kill -9 посреди commit'а**: реальный тест (`core/tests/kill_resilience.rs`
+ `core/src/bin/kill_resilience_worker.rs`) — отдельный процесс пишет
вторую (из 5000 файлов) пачку и печатает маркер прямо перед `close()`,
родительский процесс убивает его настоящим `SIGKILL` (`Child::kill()`) с
21 разной микрозадержкой (0мкс…5мс) относительно маркера. Обнаружена
резкая граница перехода между ~1.7мс и ~1.9мс (там укладывается вся
последовательность записи commit'а на этом объёме) — по обе стороны
границы, при любой из 21 задержки, контейнер после kill either полностью
в старой версии (200 файлов, entries из первого close()), либо полностью
в новой (5200) — никогда не порван и никогда не отказывается открываться.
Подтверждает атомарность двойной буферизации Commit Pointer (FORMAT.md
§6a) под реальным `SIGKILL`, а не только логическим рассуждением о коде.

**Нагрузочное тестирование**: Фаза 15 уже закрыла "много мелких файлов"
(100k–300k). Эта фаза добавила "один большой файл" —
`core/examples/large_file_bench.rs`, реальный round-trip на 2 ГиБ:
импорт (шифрование+запись) — 3.98с (~514МБ/с), экспорт (расшифровка+
чтение) — 5.84с (~352МБ/с), BLAKE3-хэш экспортированного файла **совпал**
с хэшем исходного (не просто "не упало" — криптографически подтверждённая
целостность), плюс 511 точечных проверок `read_at()` на границах блоков
(4МиБ) byte-for-byte — самое частое место off-by-one ошибок при склейке
соседних блоков — все совпали.

**Правки по репорту пользователя после первого реального использования**
(три независимых бага, найдены вживую на телефоне при первой установке —
не гипотетические):

1. **Потеря файлов при первом выходе** (Android) — `close_container()` в
   `bindings/android/src/lib.rs` вынимает `Container` из
   `Mutex<Option<_>>` и коммитит на диск, пока пользователь мог всё ещё
   ждать завершения `import_file()`/`create_folder()` (Core мутирует File
   Table только в памяти — реальный commit происходит исключительно в
   `close()`, тот же принцип, что и в kill-9 тесте выше). Быстрый "Выход"
   сразу после загрузки успевал закрыть контейнер раньше, чем импорт
   домутировал таблицу, и файл терялся молча (следующий вызов просто
   получал `AndroidError.Closed`, а экран к этому моменту уже сменился на
   Welcome). Исправлено в `LibraryScreen.kt`: все операции записи
   (`launchWrite`) регистрируют свой `Job` в `pendingWrites`, кнопка
   "Выход" сначала дожидается `pendingWrites.joinAll()` и только потом
   вызывает `closeContainer()`. Корректность не зависит от точного тайминга
   гонки — гарантируется однопоточной моделью событий Android main thread
   (регистрация Job в `pendingWrites` при запуске корутины happens-before
   любой более поздний клик на том же потоке).
2. **`OutOfMemoryError` на импорте больших файлов** (Android) — найден при
   верификации фикса №1: та же `importLauncher` читала выбранный файл
   ЦЕЛИКОМ в `ByteArray` (`openInputStream(uri)?.use { it.readBytes() }`)
   перед `importFileFromBytes()`. На файле 524МБ это гарантированно
   крашило процесс (`Failed to allocate a 524288016 byte allocation... growth
   limit 201326592` — Dalvik/ART ограничивает кучу приложения без
   `largeHeap` примерно 192-256МБ, независимо от таймингов гонки). Именно
   это, а не сама гонка, было причиной "прыжка на домашний экран" при
   попытках воспроизвести баг №1 с большим тестовым файлом. Исправлено:
   `importLauncher` теперь копирует SAF `content://`-поток во временный
   файл в `cacheDir` небольшим буфером (`copyTo()`), затем вызывает уже
   существующий `container.importFile(path, parentId)` — Core читает файл
   блоками по `block_size` через `File::open()`, не требуя буферизации
   (`write_blocks_from_reader()`, `core/src/container/mod.rs`). Имя из
   SAF-провайдера (недоверенный источник) очищается до последнего
   компонента пути перед использованием в качестве имени файла — иначе
   `../`-подобное имя могло бы вывести временный файл за пределы своей
   директории. Проверено вживую на эмуляторе: файл 500МБ импортируется без
   краша, переживает выход/повторный вход без потерь.
3. **Папки в category-вкладках (Фото/Видео/Документы) не отображались в
   самих себе** (Android **и** Desktop) — обе платформы строили эти
   вкладки как плоский `search(category=...)` без привязки к папке (тот
   же паттерн, что и виртуальные разделы Фазы 10), поэтому папка,
   созданная во вкладке "Фото", попадала только в общую "Библиотеку".
   Исправлено на обеих платформах одинаково: category-вкладки теперь
   настоящая навигация по папкам (`listDir()`/`list_dir()` текущей папки
   вместо плоского поиска), с фильтром файлов по категории на клиенте
   (`categoryOf()` в `FileKind.kt` / `category_of()` в новом
   `file_kind.py`, зеркало `Core::categorize()`) — папки показываются
   всегда независимо от содержимого, файлы — только совпадающей
   категории. Загрузка/создание папки в этих вкладках теперь кладёт
   результат в текущую (под-)папку категории, а не в корень. Проверено
   вживую: Android — эмулятор (создание папки во вкладке "Фото", загрузка
   фото внутрь неё, кросс-проверка что та же папка с документом не
   показывает фото в "Документах" и наоборот); Desktop — через реальные
   Qt-виджеты и настоящий `.slr`-контейнер (`MainWindow` напрямую,
   `QT_QPA_PLATFORM=offscreen`, без X11/Wayland-автоматизации ввода,
   которая на этой машине недоступна) — идентичный сценарий, все проверки
   прошли на невидоизменённых `_refresh_content()`/`_on_item_activated()`/
   `_import_path()`.

**Саморевью крипто-части** (`docs/SECURITY_SELF_REVIEW.md`, с самого
начала документа помечено крупным шрифтом как НЕ замена независимому
аудиту): ручной построчный обход `crypto/{kdf,aead,keys}.rs`,
`format/{keyslots,data_blocks,file_table,superblock,free_map,login_log}.rs`
и всех точек входа в `container/mod.rs`, тем же методом, что нашёл 3
бага в Фазе 17 (сначала чтение кода, потом фиксация находок, не
наоборот). Найдено и **исправлено** 4 реальные проблемы:

1. Верхней границы на параметры Argon2id (`memory_kib`/`iterations`/
   `parallelism`) в keyslot не было — тот же класс бага, что три
   находки Фазы 17 (пред-аутентификационное значение используется без
   проверки), только в измерении "стоимость вычисления": подделанный
   слот мог заставить честного пользователя попытаться выделить
   единицы-десятки ГиБ под Argon2id на своём же устройстве при попытке
   войти в свой же аккаунт. Добавлена верхняя граница (256 МиБ / 64
   итерации / 16 потоков) и на запись, и на чтение слота + тест
   `forged_huge_kdf_memory_kib_rejected_not_oom`.
2. `Dek` уже был обёрнут в `ZeroizeOnDrop`, но производные ключи (KEK
   из Argon2id, HKDF-подключи для File Table/блоков данных/etc.) —
   голые массивы, ничем не зачищаемые по выходу из скоупа. Обёрнуты в
   `Zeroizing<[u8; N]>` (~15 мест вызова, все прошли без изменений
   благодаря `Deref`/`DerefMut`).
3. `unlock()` заявлял (в собственном комментарии), что не даёт
   перечислять username по содержимому ответа — но давал по **времени**
   ответа: несуществующий username отвечал мгновенно, существующий с
   неверным паролем — после полного прогона Argon2id (~30мс).
   Для Web-бэкенда (самая широкая поверхность атаки в проекте,
   THREAT_MODEL.md §2.4) готовый сетевой timing-oracle. Исправлено —
   путь "username не найден" теперь тоже прогоняет Argon2id той же
   стоимости. Эмпирически измерено через реальные PyO3-биндинги:
   32.1мс против 31.5мс (было бы: доли миллисекунды против ~30мс).
4. **Самое существенное**: блоки данных шифруются одним общим на весь
   контейнер ключом, и AEAD-вызовы не использовали Associated Data —
   тег аутентифицировал "этот ciphertext запечатан этим ключом с этим
   nonce", но не "этот ciphertext принадлежит именно этому файлу и
   именно этой позиции". Тот, у кого есть доступ на запись к `.slr` (но
   нет пароля), мог физически переставить байты одного валидного блока
   на место другого — тег остаётся валиден (это буквально тот же
   `(key, nonce, ciphertext, tag)`, просто в другом месте на диске), и
   при чтении жертва молча получила бы чужой расшифрованный контент
   вместо ожидаемого. `content_hash` в File Table (BLAKE3 всего файла)
   не спасал — пишется при импорте, но нигде не проверяется на чтении.
   Исправлено — `aead::seal_aad`/`open_aad` (Associated Data), блоки
   данных кодируются с AAD = `file_id ++ block_index`, при декодировании
   AAD строится из значений, которым доверяет вызывающая сторона (File
   Table + позиция в `block_list`), не из одноимённых полей в открытом
   заголовке самого блока. Подтверждено не только модульным тестом, но
   и сквозным `block_swapped_between_files_on_disk_rejected` — создаёт
   реальный `.slr` с двумя файлами, физически переставляет байты блока
   одного файла на позицию блока другого прямо в файле на диске (то же
   действие, что совершил бы настоящий атакующий), переоткрывает и
   проверяет, что чтение проваливается вместо того, чтобы молча вернуть
   чужой контент.

Найдены, но осознанно **не исправлены** в этом проходе (см.
SECURITY_SELF_REVIEW.md за подробностями): единые для Desktop и Android
параметры Argon2id (нижняя граница OWASP-приемлемого диапазона, не
"сломанное" значение — реальное бенчмаркание под целевое железо остаётся
отдельной задачей ещё с Фазы 3); отсутствие anti-rollback защиты всего
контейнера или отдельных регионов (формат даёт атомарность против
*обрыва* записи, не против *намеренной* подмены на более старую валидную
версию — требует отдельного проектирования, не точечного фикса);
password/recovery-фраза как обычный `String` на границе Core↔Python —
фундаментальное ограничение иммутабельности строк в CPython, не то, что
чинится патчем в Core.

`cargo test --workspace` — 64 unit/integration-теста в `cove-core` (было
59 после Фазы 17), все зелёные, включая полный интеграционный `kill -9`-
тест (~102с). Python-биндинги пересобраны, все существующие GUI smoke-
тесты (навигация, файловые операции, библиотека, пользователи, настройки
безопасности) перепрогнаны без регрессий.

**Механизм обновлений с проверкой подписи.** По прямому запросу —
сценарий "уведомить + ссылка на скачивание", НЕ автозамена бинарника
(осознанно: risk/reward не в пользу авто-обновления для Windows-сборки
без code-signing сертификата, ROADMAP.md Фаза 16, — самозаменяющийся
процесс на Windows к тому же должен разбираться с файлом, занятым самим
собой). Обе платформы (Desktop и Android — тоже по прямому запросу,
не только Desktop) сразу.

Протокол одинаковый на обеих платформах: `scripts/sign_release.py`
считает SHA-256 каждого артефакта релиза, собирает `release-manifest.json`
(версия + хэши) и подписывает его Ed25519-ключом
(`release-signing-key.pem`, сгенерирован `openssl genpkey -algorithm
ed25519`, реальный keypair, не заглушка — приватный ключ в .gitignore,
`release-signing-key.pem.example` — инструкция по генерации своего и по
секрету `RELEASE_SIGNING_KEY` для CI). `release.yml` — новый job
`sign-release` между сборкой артефактов и `publish-release`, публикует
`release-manifest.json`/`.sig` как дополнительные assets релиза.

Проверка на телефоне/десктопе: скачивает **только** манифест и подпись
(килобайты, не сам установочный файл), проверяет подпись Ed25519
встроенным публичным ключом (одинаковый на обеих платформах — `desktop/
app/update_check.py` и `android/.../update/UpdateChecker.kt`,
`RELEASE_PUBLIC_KEY_B64`), сравнивает версию, показывает
"Проверить обновления" → результат + кнопку на страницу релиза
(Desktop — новая вкладка "Обновления" в настройках, реализована через
`QThread`, чтобы сетевой запрос не подвешивал диалог; Android —
секция в `SettingsScreen.kt`, `rememberCoroutineScope`). Реальная
защита, которую даёт именно подпись (а не просто HTTPS до
api.github.com): скомпрометированный CDN/зеркало или MITM на самом
GitHub API не могут подсунуть приложению поддельный номер версии —
подпись не сойдётся и попытка будет честно отклонена, а не тихо
проигнорирована (`verify_manifest_signature`/`verifyManifestSignature`
кидают исключение, а не возвращают `bool`, — тот же принцип "нельзя
случайно проигнорировать провал", что и в остальной крипто-части
проекта, docs/SECURITY_SELF_REVIEW.md).

Android потребовал BouncyCastle (`bcprov-jdk18on`) — нативная поддержка
Ed25519 в `java.security` появилась только в API 33, а `minSdk` здесь 24
(Фаза 14). Заодно добавлено `android.permission.INTERNET` — первый
случай, когда Android-приложению вообще нужен исходящий сетевой доступ
(Web-доступ — это Desktop раздаёт по сети, а не Android стучится наружу).

**Проверено по-настоящему, не только "собирается"**: 7 тестов на
Python-стороне (`desktop/test_update_check.py` — валидная подпись,
подделанный манифест, чужой ключ, сравнение версий, и три сценария
`check_for_updates()` целиком с замоканным HTTP-слоем, но настоящей
Ed25519-подписью) и 6 на Kotlin-стороне (`UpdateCheckerTest.kt`,
`./gradlew testDebugUnitTest` — реальный JVM-прогон, не просто
компиляция; `org.bouncycastle.util.encoders.Base64` вместо
`android.util.Base64` в проде специально, чтобы код был тестируем на
голой JVM без Robolectric). Плюс `gui_update_settings_test.py` —
Desktop-диалог настроек целиком через реальный `QThread` и Qt-сигналы

**Архитектурное изменение по прямому запросу пользователя: запись на диск
сразу после действия, а не только при `close()`.** Пока разбирались с
предыдущим багом (фото из Desktop не видно в Web), выяснилось, что причина
глубже: Core с самого начала (см. `container/mod.rs`) держит все мутации
File Table только в памяти сессии и пишет их на диск исключительно в
`close()` — так что две одновременно открытые сессии (Desktop + Web на
одном контейнере) не видели изменений друг друга, пока одна из них не
закрывалась целиком. Пользователь прямо попросил это исправить — "чтобы
писалось сразу на диск", а не заставлять перезаходить.

`Container::close(self)` разобран на `commit(&mut self)` (новый, не
потребляет `self` — можно звать сколько угодно раз за сессию: перекодирует
File Table/Free Map/журнал входов и один атомарный переключатель Commit
Pointer, FORMAT.md §6a) и тонкую обёртку `close()` = `commit()` + drop.
Второй `commit()` в той же сессии — не бесплатная операция (полное
перекодирование File Table), поэтому НЕ вызывается на каждый низкоуровневый
вызов Core автоматически (иначе batch-импорт из тысяч файлов стал бы
квадратичным по времени — тот же класс проблемы, что фаззинг нашёл в Фазе
17), а вызывается один раз на пользовательское действие на стороне
GUI/актора:

- **Web** (`web/backend/src/actor.rs`) — одна точка на всех: новая
  `commit_if_ok()` вызывается после каждой успешной мутирующей `Command`
  (CreateFolder/Import/Delete/Restore/Rename/Move/SetFavorite) прямо в
  диспетчере актора — ни один HTTP-хендлер в `routes.rs` трогать не
  пришлось.
- **Desktop** (`main_window.py`) — новый `_commit()` вызывается в `else:`-
  ветке после import/новая папка/переименование/удаление/избранное/
  восстановление/замена содержимого. Batch-импорт (drag&drop нескольких
  файлов, `_handle_dropped_files`/`_import_files_dialog`) коммитит **один
  раз после всего списка**, не на каждый файл.
- **Android** (`LibraryScreen.kt`) — новый `commitQuietly()` после
  import/новая папка/удаление/избранное; SAF-пикер отдаёт один файл за
  раз, так что квадратичный сценарий тут физически невозможен.
- `add_user`/`remove_user`/`change_password`/`set_user_role` **не
  трогались** — они и так пишутся точечно сразу (`write_keyslot_at`),
  commit() им не нужен (см. исходный комментарий у `close()` — "Keyslots в
  commit не участвуют").
- Генерация миниатюр (`thumbnail()`) **сознательно исключена** — вызывается
  по одной на каждый видимый файл в гриде при скролле/открытии раздела,
  commit() там означал бы ту же квадратичную стоимость. Миниатюра — кэш,
  регенерируемый из оригинала, не пользовательские данные: потерять её при
  крэше не так важно, как потерять файл.

Три биндинга получили новый метод: `PyContainer.commit()` (Python),
`AndroidContainer.commit()` (UniFFI — Kotlin-биндинги пересобраны заново
скриптом, не отредактированы вручную).

**Проверено по-настоящему, вплоть до точного повторения репорта
пользователя**:
- Новый `cargo test`: `container::tests::commit_without_close_is_visible_to_a_second_reader`
  — создаёт контейнер, второй читатель до commit() видит пустоту, после
  `commit()` (без close()!) видит файл, первая сессия остаётся рабочей и

**Критический фикс по репорту пользователя: тихая потеря данных при
одновременных сессиях (самая серьёзная находка этой фазы).** Пользователь
создал папку в Desktop, разлогинился, зашёл заново — папки не было ни в
Desktop, ни в Web. Прямое воспроизведение через реальные `cove_core_py`-
биндинги на копии реального контейнера подтвердило: `commit()`/`close()`
отрабатывали без единой ошибки, но папка всё равно исчезала.

Причина — не баг конкретной операции, а дыра в самой модели `commit()`
из предыдущего раздела: он писал **безусловно**, не проверяя, не успел ли
кто-то другой закоммитить раньше. Сценарий: сессия A (Desktop) создаёт
папку и коммитит первой — на диске папка есть. Сессия B (залипшая вкладка
Web, открытая ДО этого момента) держит в памяти старый File Table **без**
папки; когда B в какой-то момент коммитит или закрывается — её устаревший
File Table молча перезаписывает диск, стирая работу A. Это ухудшение уже
задокументированного риска ("нет file-level advisory locking"): раньше
перезапись происходила только на полном `close()`, теперь, когда `commit()`
можно звать сколько угодно раз за сессию, окно для такой перезаписи
открывается на порядок чаще.

Исправлено на уровне формата, не патчем в GUI:

1. **Optimistic concurrency control.** `Superblock.version_counter`
   (существующее поле FORMAT.md §4, раньше использовалось только для
   rollback-резерва) теперь ещё и токен синхронизации сессии. В начале
   `commit()` текущий указатель коммита читается с диска и сверяется с
   тем, что сессия видела в последний раз (`unlock()` или прошлый
   `commit()`). Несовпадение = кто-то другой закоммитил раньше.
2. **Новая категория ошибки `CoveError::Conflict`** (+ `CoveConflictError`
   в Python, `AndroidError::Conflict` в Kotlin, HTTP 409 в Web) —
   добавлена в `ErrorCategory` по правилам ARCHITECTURE.md §3, прокинута
   во все три биндинга.
3. **Флаг `dirty`** на `Container` — разруливает asymmetry между "у меня
   есть несохранённые правки" и "я просто держала сессию открытой". При
   расхождении версий: если `dirty` — громкий `Conflict` (пользователь
   должен узнать, что его правка не сохранилась, а не тихо её потерять);
   если НЕ `dirty` — тихий no-op, ничего не пишем поверх чужого (жертвуем
   только записью этой сессии в login_log — разумный компромисс: журнал
   входов и так не гарантированно консистентен при параллельных сессиях,
   а вот пользовательские файлы/папки терять нельзя). Без dirty-флага
   первая же попытка проверить эту защиту тестом ловила ложные срабатывания
   — безобидная читающая сессия рушила commit() у настоящего писателя;
   нашлось сразу, когда обновлённый `commit_without_close_is_visible_to_a_second_reader`
   упал с `Conflict` там, где не должен был.
4. **Web (`actor.rs`)**: `commit_or_conflict()` — если commit() после
   успешной в памяти мутации вернул `Conflict`, HTTP-ответ клиенту
   подменяется на ошибку вместо честного на вид, но лживого "200 OK":
   раньше `commit_if_ok()` эту ошибку проглатывал молча, то есть сам
   сервер был бы источником точно такой же тихой потери данных, если бы
   веб-сессия коммитила поверх более новых изменений с другой платформы.

**Проверено по-настоящему**, включая тест, который был красным до
добавления dirty-флага и зелёным после (не просто "написали тест, он
прошёл"):
- `stale_read_only_session_does_not_erase_concurrent_commit` — сессия A
  создаёт папку и коммитит; сессия B, открытая раньше и ничего не
  менявшая, закрывается позже — папка A переживает закрытие B.
- `stale_session_with_pending_edit_gets_loud_conflict_not_silent_loss` —
  тот же сценарий, но у B есть своя правка — `commit()` возвращает
  `Err(Conflict)`, не тихий успех и не тихую потерю чужой папки.
- `commit_without_close_is_visible_to_a_second_reader` (из предыдущего
  раздела) обновлён и перепроверен — не потребовалось менять сам фикс,
  только явно не звать `close()` на чисто читающих сессиях в тесте (как и
  задумано dirty-флагом).
- 68 unit/integration-тестов в `cove-core` (было 66) + полный `kill -9`-
  тест (commit() теперь вызывается кратно чаще — резилиенс к обрыву
  посреди записи перепроверен на возросшей частоте, не только логически).
- Все три собранных этой фазой процесса (Desktop `main.py`, оба
  `cove-web-backend` на 8443/8444) требовали живого перезапуска —
  Python `.so` и Rust-бинарники, загруженные в память ДО пересборки, не
  подхватывают код с диска сами по себе. Уже запущенный Desktop-процесс
  был безопасно остановлен через `SIGTERM` (не вызывает `closeEvent`/
  `close()`, значит не мог тихо закоммитить свой устаревший File Table
  поверх реальных папок пользователя) и перезапущен на свежей сборке —
  реальные пользовательские папки (`veo`/`vid2`/`test2`) подтверждены на
  диске до, во время и после всех перезапусков.

**Правка по репорту пользователя: загрузка видео в веб-версии падала с

всему роутеру — остальные ручки принимают только маленький JSON, незачем

`import_file_from_bytes` держит файл целиком в памяти (в отличие от
потокового `import_file` у Desktop/Android, ROADMAP.md Фаза 7/14) —
честно задокументировано как известное ограничение MVP-фронтенда, не
недосмотр.
**Проверено вживую**: 1 МБ грузился и раньше (200), 5 МБ падал с той же
ошибкой, что в репорте — до фикса; после фикса 20 МБ грузится (200),
файл подтверждён на диске (`screen.mp4`, размер сходится байт в байт).
Ваш реальный веб-сервер на 8443 перезапущен на исправленной сборке.

**Новая фича по прямому запросу пользователя: живая синхронизация между
одновременно открытыми сессиями.** Всё предыдущее в этой фазе (commit(),
optimistic concurrency) чинило только ЗАПИСЬ — гарантировало, что
изменения не терялись и не затирались чужими. Но уже открытая сессия
никак не подхватывала ЧУЖИЕ изменения сама: Desktop, однажды прочитав
File Table при входе, держал его в памяти неизменным до логаута, даже
если на диске давно лежала более новая версия. Пользователь прямо
попросил: "загрузил в вебе — хочу видеть сразу в ПК", без перезахода.

`Container::reload(&mut self) -> Result<bool>` — новый метод в Core,
симметричный `commit()`: если на диске более новая версия, перечитывает
File Table/Free Map/журнал входов (пароль не нужен — DEK уже в памяти
сессии, тот же путь расшифровки регионов, что в `unlock_slot()`, без
повторного KDF). Возвращает `false` без единого лишнего чтения, если
версия та же — дешёвая проверка на каждый вызов, не полный обход
контейнера. Если у сессии есть свои несохранённые правки (`dirty`) —
`Conflict`, тем же принципом, что и `commit()`: подменять недокоммиченное
состояние пользователя чужим было бы так же нечестно, как его тихо терять.

Прокинуто по всем трём платформам по-разному, под их архитектуру:
- **Web** (`actor.rs`) — `reload()` вызывается перед КАЖДОЙ командой в
  диспетчере актора. Web не держит долгоживущий "экран" как Desktop — у
  него просто каждый HTTP-запрос новый (открыл вкладку, обновил
  страницу), так что это даёт синхронизацию бесплатно, без отдельного
  таймера или изменений во фронтенде.
- **Desktop** (`main_window.py`) — новый `QTimer` на 3 секунды
  (`_live_sync_timer`) тихо вызывает `reload()` и перерисовывает список,
  только если что-то реально изменилось (не дёргает UI/выделение почём
  зря). Кнопка "Обновить" теперь тоже сначала зовёт `reload()` — раньше
  она просто перерисовывала уже устаревшую память. Таймер корректно
  останавливается в `_teardown_auto_lock()` при логауте/закрытии — тот же
  метод, что уже останавливал таймер автоблокировки, вызывается из тех же
  двух мест (`_logout()`/`closeEvent()`).
- **Android** — `AndroidContainer.reload()` добавлен в биндинги для
  единообразия API между платформами, но НЕ подключён к UI в этом проходе
  (запрос был именно про Desktop↔Web) — сознательно не расширяю объём
  сверх того, что просили.

**Проверено по-настоящему, включая сквозной сценарий без единого
перезахода ни с одной стороны**:
- Новый `cargo test`: `reload_picks_up_changes_from_another_session_without_password`

**Правка по репорту пользователя (со скриншотом): значки папок в сетке
Desktop были заметно крупнее файлов, подпись с именем папки обрезалась.**
Не связано с превью видео напрямую — стало заметно именно теперь, когда
рядом появились настоящие превью для сравнения. Причина: `QIcon.pixmap
(size)` у системной иконки папки (`SP_DirIcon`, из иконок темы) **никогда
не увеличивает картинку сверх "родного" разрешения темы** — проверено
вживую: тема на этой машине даёт максимум 128×128, при запросе 160×160
(или крупнее, для "Крупные" миниатюры) честно возвращает те же 128×128,
а не масштабирует. В отличие от простого `QIcon(QPixmap)` (как у
настоящих превью фото/видео, где итоговый файл уже готового целевого
размера), у иконок из темы это создавало рассинхрон с тем, что
`QListWidget` рассчитывает под сетку через `setGridSize()`/`setIconSize()`.

Исправлено — `_sized_standard_icon()`: берём что дала тема, рисуем на
пустом `QPixmap` ровно нужного размера через `QPainter` (по центру, без
растяжения/искажения пропорций) и оборачиваем в новый `QIcon`. Тот же
принцип, что уже работает для превью — простой pixmap-based `QIcon`
ведёт себя предсказуемо для раскладки.
**Проверено по-настоящему**: до фикса `raw_icon.pixmap(QSize(160,160))`
возвращал `128×128`; после — `wrapped_icon.pixmap(QSize(160,160))`
возвращает ровно `160×160`, и `availableSizes()` тоже `[160×160]` —
единственный заявленный размер, без двусмысленности для раскладки.
Desktop перезапущен на исправленной сборке.

**Правка та оказалась необходимой, но не достаточной** — пользователь
после перезапуска сообщил "ничего не поменялось" с тем же скриншотом.
`_sized_standard_icon()` действительно чинил размер pixmap'а (проверено
выше API-вызовами), но сам видимый баг (обрезанная/пропавшая подпись)
жил не в размере иконки, а в раскладке элемента списка — API-проверка
размера пикселей не эквивалентна проверке того, что реально нарисовано
на экране, и этого было недостаточно, чтобы считать баг закрытым.

Раскопано через реальный `QWidget.grab()` → PNG (в этом окружении нет
рабочего X11/Wayland-скриншотера, а офскрин-скриншот через `grab()` — в
связке с `QT_QPA_PLATFORM=offscreen` — единственный надёжный способ
увидеть, что Qt реально нарисовал) на настоящем `MainWindow` поверх
реального контейнера пользователя, а не на заглушечных данных:
- Скриншот воспроизвёл баг один в один: у иконок папок подписи не видно
  вообще, у видео-превью — видно.
- Диагностика показала: pixmap иконки папки — верные `160×160` (фикс
  выше сработал), у видео-превью — `160×90` (letterbox по пропорциям), но
  `visualItemRect` у обоих элементов **одинаковый**, `166×110` — то есть
  сам размер pixmap'а тут ни при чём.
- Увеличение `setGridSize()` (пробовал 208→280→320 по высоте, с полным
  `_refresh_content()` после каждого) — **не дало вообще никакого эффекта**
  на видимую подпись. Это исключило "не хватает места в ячейке" как причину.
- Подмена одной иконки папки на маленький тестовый pixmap 100×100 —
  подпись частично проявилась. Это доказало, что дело в высоте пикселей
  самой иконки, а не в размере сетки.
- Явный `item.setSizeHint(...)` поверх уже добавленных элементов —
  подпись появилась полностью.

**Настоящая причина**: `QListWidgetItem.sizeHint()` по умолчанию
`(-1, -1)` — Qt сам считает высоту ячейки через делегат, и для
полноразмерных квадратных иконок (папка, `SP_FileIcon` — во весь
`iconSize`) это авторасчёт занижал итоговую высоту настолько, что текст
подписи обрезался/пропадал целиком. У видео/фото превью баг не был
заметен ровно потому, что `KeepAspectRatio` даёт им реальную высоту
меньше `iconSize` — они случайно помещались в заниженный авторасчёт.

**Фикс** — в `_refresh_content()` (`desktop/app/main_window.py`) каждому
`QListWidgetItem` явно выставляется `item.setSizeHint(grid_size)` (тот же
`gridSize()`, что и так уже настроен на списке) сразу после создания —
это заставляет делегат использовать переданный размер вместо
собственного заниженного авторасчёта.

**Проверено по-настоящему**, тем же способом (`grab()` → PNG, реальный
`MainWindow` поверх реального контейнера, реальный проход через
production-метод `_refresh_content()`, не точечный патч в тестовом
скрипте) — на всех трёх вкладках, где встречаются папки: "Видео" (папки
"veo"/"vid2"/"test2" — подписи видны, видео-превью с подписью тоже),
"Фото" (папки "test22"/"rrrrr" — подписи видны, фото-превью не
регрессировали) и "Библиотека" (те же папки и файлы вперемешку — тоже
без регрессий). Desktop перезапущен на этой сборке.

**Закрыты задним числом три реальных долга Core, честно оставленных
незакрытыми ещё с Фазы 2/6/15 (по прямому запросу пользователя — "1.2.3
пункт давай" после разбора ROADMAP.md на предмет незавершённого):
компактификация, точечная запись File Table, восстановление при частичном
повреждении.** Все три оказались связаны сильнее, чем казалось из текста
самих пунктов — реализовывались вместе.

**Аудит перед началом**: `free_blocks: Vec<u64>`/Free Map существовали в
формате с Фазы 2, но переменная НИКОГДА не заполнялась ни одним методом —
`delete_file`/`replace_file_content` честно комментировали "блоки остаются
орфанами до компактификации", но сама компактификация не была написана ни
в Фазе 2, ни в обещанной Фазе 15 (которая в итоге занялась другим —
`next_file_id`, распараллеливанием — по факту реального профилирования, не
по плану). `Superblock.file_table_backup_offset` тоже писался в каждом
commit с Фазы 2, но ни разу не читался — второй найденный, а не только
задокументированный, долг.

**1. Точечная (постраничная) запись File Table** (`format/file_table.rs`,
`container/mod.rs`) — раньше `commit()` перешифровывал (AEAD-seal) ВСЮ
таблицу целиком при любой правке, даже одной записи в последней странице
из тысяч. Новая `encode_file_table_incremental()` переиспользует уже
закодированные байты страниц из кэша (`Container::file_table_page_cache`)
для страниц, чей номер не попал в `dirty_pages` — а сам номер страницы
теперь точно отслеживается в каждом мутирующем методе
(`import_file`/`create_folder`/`rename_file`/`move_file`/`set_favorite`/
`thumbnail`/`replace_file_content` — через позицию в `Vec`, у push —
последняя страница, у `iter_mut().find()` переписано на
`iter().position()` + индексацию, чтобы позиция была известна). Операции,
сдвигающие позиции всех последующих записей (`retain()` — окончательное
удаление из корзины, чистка миниатюр) помечают грязными ВСЕ страницы
целиком — точный пересчёт сдвига легко сделать с ошибкой на единицу, а
сами эти операции на порядок реже точечных правок, так что цена
консервативности незначительна. Страница остаётся тем же самым
шифртекстом (свой nonce на страницу, как и раньше) — просто на новом
физическом offset'е, инвариант crash-safety (двойная буферизация Commit
Pointer, FORMAT.md §6a) не меняется.
**Найден и исправлен реальный баг при первой попытке** (не гипотетический
— поймали существующие тесты `commit_without_close_is_visible_to_a_second_reader`
и `reload_picks_up_changes_from_another_session_without_password`): если
включить переиспользование кэша, но не отслеживать `dirty_pages` в
мутирующих методах, `commit()` молча пишет на диск СТАРУЮ (закэшированную
при unlock) версию страницы вместо новой — новая папка/файл проходят
`self.dirty = true`, но реально теряются при следующем commit. Оба теста
упали именно так при первой попытке; после того как каждый мутирующий
метод стал явно звать `mark_page_dirty_for_position()`/
`mark_all_pages_dirty()`, все 73 существовавших теста снова прошли.
**Проверено дополнительно**: новый `commit_after_partial_edit_survives_close_reopen_across_pages`
— таблица на 2 страницы, правка одной записи во второй, `commit()`,
закрытие/переоткрытие — все записи (включая нетронутую первую страницу)
на месте; плюс модульные тесты в `file_table.rs`
(`incremental_encode_reuses_untouched_pages` — сверяет закодированные
байты нетронутой страницы побайтово между двумя commit'ами,
`incremental_encode_shrinks_cache_when_pages_removed`).

**2. Восстановление при частичном повреждении File Table** (`format/file_table.rs`,
`container/mod.rs`) — новая `decode_file_table_lenient()` не считает
повреждение (провал AEAD-аутентификации) ОДНОЙ страницы фатальным для
всего блоба: внешняя framing-структура (длины страниц) читается отдельно
от их зашифрованного содержимого, поэтому повреждение содержимого одной
страницы не мешает найти и прочитать остальные. `unlock()`/`reload()`
используют её вместо строгой версии, записи всех уцелевших страниц
собираются в File Table как обычно, а номера потерянных страниц кладутся
в новое поле `Container::lost_file_table_pages()` (чисто информационный
метод — GUI может проверить и честно предупредить пользователя, ничего не
скрывая, но ничего и не обязано делать с этим сейчас). Дополнительно —
второй, более грубый уровень защиты, которого не было вообще: если
основной блоб File Table не читается СТРУКТУРНО целиком (не про
отдельные страницы — framing сломан полностью, например от усечения
файла), `read_file_table_with_recovery()` в последний момент пробует
`Superblock.file_table_backup_offset` — предыдущую валидную версию,
указатель на которую пишется в каждом commit с Фазы 2, но который до этой
правки не читался вообще ни одной строчкой кода. Честное ограничение:
Superblock хранит только offset резервной версии, не её длину (она была
известна только в момент того commit'а) — читаем с запасом до конца
файла, framing внутри блоба сам определяет, где реально заканчивается,
лишний хвост в буфере просто не читается.
**Проверено по-настоящему**: `lenient_decode_recovers_all_but_corrupted_page`
(намеренно портит AEAD-шифртекст ровно одной страницы из трёх, сверяет,
что все записи ДВУХ других страниц восстановились, а не только "что-то
осталось") и `reopen_with_one_corrupted_page_recovers_the_rest` — тот же
сценарий на уровне полного `Container`: реальный контейнер с 3 страницами
записей, порча байта прямо в файле на диске, переоткрытие — контейнер
открывается (не отказывает), `lost_file_table_pages()` непусто, часть
записей доступна, часть честно потеряна.

**3. Компактификация свободных блоков** (`container/mod.rs`, новый
`Container::compact()`) — единственная операция, которая физически
уменьшает файл контейнера. Формат Cove append-only и для метаданных
(каждый `commit()` дописывает новые версии File Table/Free Map/Login
Log/Superblock в конец файла, старые версии остаются на диске), и для
данных (удалённые/перезаписанные файлы оставляют блоки-орфаны) — файл
только растёт. `compact()` пересобирает контейнер заново в отдельный
временный файл (`<path>.compact.tmp`): header и keyslots копируются байт-
в-байт (без риска байтового расхождения от повторной сериализации
обёрнутых ключей), блоки данных живых записей (по текущей File Table в памяти)
переносятся **вербатим** — без расшифровки/повторного шифрования, только
смена offset'а (безопасно: AAD блока привязан к `(file_id, block_index)`,
не к положению в файле, `data_blocks::block_aad`) — а File Table/Free
Map/Login Log/Superblock перекодируются с нуля. Атомарность — тот же
принцип, что и у обычного commit: временный файл целиком пишется и
`fsync`'ится, и только потом `std::fs::rename()` атомарно подменяет
исходный; при любой ошибке в процессе исходный файл остаётся нетронутым
и рабочим. Требует прав администратора (как `add_user`/`remove_user`) и
явного вызова — дорогая операция, не часть обычного commit(). Как и весь
остальной Core, без межпроцессной блокировки — тот же документированный
класс ограничения, что и у commit()/reload() (Фаза 13).
**Проверено по-настоящему** (не просто "не упало"): `compact_reclaims_space_from_orphaned_blocks`
— импорт живого файла + 2 МиБ файла, окончательное удаление второго,
commit, `compact()` — реально освобождено больше 1 МиБ (`freed ==
size_before - size_after`, не просто "не ноль"), живой файл после
компактификации по-прежнему читается байт-в-байт правильно, включая после
закрытия/переоткрытия (новые offset'ы блоков честно попали в File Table);
`compact_preserves_other_users_login` — второй пользователь реально
логинится своим паролем после компактификации, не только "байты
keyslot'а совпадают"; `compact_requires_admin` — read-only пользователь
получает `PermissionDenied`; `compact_with_nothing_to_reclaim_is_a_safe_noop`.

**Биндинги**: `compact()`/`lost_file_table_pages()` добавлены в PyO3
(`bindings/python`) и UniFFI (`bindings/android`) тем же способом, что и
`reload()` раньше — 1:1 проброс, `usize` заменён на `u32` для Android (не
FFI-тип UniFFI). GUI-кнопки/экраны для вызова `compact()` сознательно НЕ
добавлены в этом заходе — не запрашивались, отдельная по объёму задача

**Проверено по-настоящему, не только компиляцией**: `cargo test -p

на восстановление/точечную запись на уровне Container, плюс 4 в

**Доработка по прямому запросу пользователя сразу после предыдущей записи:
"надо чтобы после удаления файла база становилась легче" — раньше
`compact()` был реализован, но вызвать его было неоткуда (ни кнопки в UI,
ни автоматического триггера), так что на практике удаление файла **не**
уменьшало файл `.slr` вообще, только помечало запись удалённой внутри
самой базы.**

Обсудили с пользователем компромисс явно, а не выбрали молча: компактить
на каждое удаление слишком дорого (`compact()` целиком переписывает файл
контейнера — 50 последовательных удалений означали бы 50 полных
перезаписей), компактить "раз в N удалений/по объёму орфанов" сложнее и
менее предсказуемо для пользователя. Выбран третий вариант — **компактить
один раз при выходе/закрытии сессии, и только если за сессию реально
что-то осиротело**.

**Реализация** (`container/mod.rs`) — новое поле `Container::orphans_created:
bool`, взводится теми же тремя местами, что реально порождают
орфанов-блоков: `delete_file()` при ОКОНЧАТЕЛЬНОМ удалении (не при
перемещении в корзину — там содержимое всё ещё используется),
`replace_file_content()` (старые блоки заменяются новыми) и
`remove_thumbnail_of()`, когда она реально что-то убрала (перегенерация
миниатюры после `replace_file_content` тоже осиротяет старую). `close()`
(тот самый метод, который GUI на всех трёх платформах уже вызывает при
выходе/логауте — переписывать код Desktop/Android/Web не потребовалось)
теперь смотрит на этот флаг: если что-то осиротело — зовёт `compact()`
(который заодно и коммитит текущее состояние), если нет — обычный дешёвый
`commit()`, как и раньше.

**Заодно исправлена нестыковка в правах доступа**, найденная по ходу:
`compact()` требовал прав администратора, но обычный пользователь с
правом записи (не админ) тоже может удалять файлы — получалось, что
человек, реально породивший орфанов, не мог освободить место сам. Право
на `compact()` понижено до обычного `require_writable()` (та же граница,
что у `delete_file`/`replace_file_content`, которые эти орфаны и создают)
— это уборка за собственными действиями пользователя в рамках его
собственных прав на контент, а не операция уровня администрирования
пользователей контейнера (`add_user`/`remove_user` как были под
`require_admin()`, так и остались).

**Проверено по-настоящему**: новый `close_after_permanent_delete_shrinks_file_automatically`
— импорт живого файла + 2 МиБ файла на удаление, `commit()`, окончательное
удаление, затем **только** `close()` (без единого явного `compact()`) — файл
`.slr` на диске реально стал меньше, чем был до удаления, и живой файл
пережил цикл закрытие/переоткрытие без потерь. Обратный тест
`close_without_deletions_does_not_auto_compact` — сессия без единого
удаления после `close()` НЕ хлопывает `file_table_backup_offset` в текущий
(что делает только `compact()`, не обычный `commit()`) — доказательство,
что сработал именно дешёвый путь, а не незаметный лишний compact. Плюс
`compact_allowed_for_non_admin_writer` — пользователь с ролью ReadWrite
(не администратор) реально освобождает место после своего собственного
удаления; `compact_requires_write_permission` (переименован из
`compact_requires_admin` — тест тот же по сути, ReadOnly по-прежнему
отклоняется, но теперь по границе `require_writable`, а не `require_admin`).
82 теста Core (было 79), `cargo clippy -p cove-core --lib -- -D warnings`
— чисто. Пересобраны и переустановлены `desktop/cove_core_py.so` и Android
`.so` под все 4 ABI, живой десктоп перезапущен, реальный контейнер
пользователя по-прежнему открывается корректно (проверено вручную,
`list_dir` без ошибок — деструктивных операций на реальном контейнере
пользователя намеренно не выполнялось).

**Веб-доступ на Android** (по прямому запросу пользователя — "надо добавить
веб морду в андроид версию"). ROADMAP.md Фазы 14 сознательно откладывал это
как отдельный по объёму вопрос ("энергопотребление и жизненный цикл
процесса"), не пытаясь заранее угадать реальные риски — и они
действительно нашлись, но не совсем те, что предполагались.

**Разведка перед реализацией** (агентом, только чтение) сверила контракт
Desktop↔`cove-web-backend` (`web_server.py`: всего два флага при старте,
`--container`+`--bind`, логин уходит по HTTP уже ПОСЛЕ старта процесса —
хорошая новость: не нужно передавать разблокированный `Container` между
процессами) и вскрыла реальный, не гипотетический пробел — `--frontend-dir`
по умолчанию указывает на путь сборочной машины
(`CARGO_MANIFEST_DIR/../frontend`), и **даже упакованная Desktop-сборка
сейчас не отдаёт статику фронтенда вообще** (не копируется никаким
скриптом) — не то, что можно было скопировать под Android, пришлось решать
заново.

**1. Кросс-компиляция `cove-web-backend` под все 4 Android ABI** — до этой
правки ни строчки Axum/Tokio/TLS-стека не собиралось под Android, только
чисто-крипто граф `cove-core` через `cove-android` (UniFFI). Собралось с
первого раза для `aarch64`/`x86_64` (включая `aws-lc-sys`, самый рискованный
пункт разведки — C/ассемблер, cmake, два независимых крипто-бэкенда `ring`+
`aws-lc-rs` одновременно). `armv7`/`i686` (32-битные) не собрались — реальный
баг, не мнимый: `MAX_UPLOAD_BYTES = 4 * 1024 * 1024 * 1024` на 32-битном
`usize` (максимум `2^32 − 1`) на 1 байт превышает предел. Исправлено условной
константой (`if usize::BITS >= 64 { 4 ГиБ } else { 1 ГиБ }`) — на 32-битных
таргетах и без этого нереалистично держать в памяти файл такого размера
целиком (`import_file_from_bytes` не потоковый, ROADMAP.md Фаза 13). Все 4
ABI и Desktop-сборка (регрессия) собираются чисто после фикса.
Новый `scripts/build_web_backend_android.sh` — тот же паттерн, что
`build_android_bindings.sh`, но для `web/backend` вместо `bindings/android`.

**2. Бинарник под видом `.so` реально выполняется в песочнице приложения**
— тот же трюк, что уже подтверждён индустрией для похожих случаев:
`cove-web-backend` копируется в `jniLibs/<abi>/libcove_web_backend.so`
(не JNA-загрузка — обычный `exec()` через `ProcessBuilder`). **Найдено
вживую на эмуляторе, не в документации**: по умолчанию (`minSdk >= 23`) AGP
хранит нативные библиотеки сжатыми ВНУТРИ APK и грузит их через mmap, не
извлекая на диск (`extractNativeLibs=false`) — `ApplicationInfo.
legacyNativeLibraryDir/<abi>/` существовала, но была ПУСТОЙ (проверено
`run-as` + `ls`). `ProcessBuilder`/`exec()` нужен настоящий файл на диске.
Исправлено `android.packaging.jniLibs.useLegacyPackaging = true` в
build.gradle.kts — после этого `extractNativeLibs=true`, файл на диске с
правами `-rwxr-xr-x`, и `run-as ... libcove_web_backend.so --help` реально
печатает `clap`-хелп прямо с устройства.

**3. Статика фронтенда** — `android/app/build.gradle.kts`:
`assets.srcDirs("../../web/frontend")` — Android пакует `index.html`/
`app.js`/`style.css` прямо из существующего каталога, без дублирования
исходников и риска разъехаться с тем, что реально отдаёт Desktop-версия.
`WebServerService` извлекает эти 3 маленьких файла из assets в `filesDir`
при каждом запуске (дёшево, десятки КБ) — `--frontend-dir` читает с диска,
не из APK, компилируемого default-пути на Android физически не существует.

**4. `WebServerService.kt`** (новый пакет `webserver/`) — foreground-сервис,
Android-аналог `web_server.py`. Реальные архитектурные решения, не просто
перенос:
- FGS-тип `specialUse` вместо `dataSync` — последний с API 34+ ограничен
  таймаутом (6ч), неприемлемо для сервера, который пользователь мог бы
  держать включённым весь день; `specialUse` — официально предназначенный
  Google тип для случаев вне стандартных категорий, с обязательным
  текстовым описанием в `<property>` манифеста.
- `WebServerStatus` — синглтон-`StateFlow`, а не `bindService()`/AIDL:
  сервис и Activity живут в одном процессе, тот же принцип простоты, что и
  остальная навигация приложения (без Navigation-Compose).
- `POST_NOTIFICATIONS` запрашивается перед стартом на API 33+, но не
  блокирует запуск при отказе — деградация некритичная (сервис работает,
  просто без видимого уведомления).
- Логи процесса — в logcat (`Log.i`), не `DEVNULL` — тот самый урок из
  `web_server.py` про невидимые ошибки, только на этот раз применённый
  заранее, а не после жалобы.
- Мягкая остановка (`destroy()` → `waitFor(5с)` → `destroyForcibly()`) —
  тот же паттерн, что `WebServerManager.stop()` на Desktop.

**5. `SettingsScreen.kt`** — секция "Веб-доступ": порт (персистится через
новый `AppSettings.webPort()`), статус (Stopped/Starting/Running(port)/
Error), кнопка старт/стоп, локальный LAN IP (`NetworkInterface`-перебор —
Android-аналог `_local_lan_address()` с Desktop, там `socket.gethostbyname`
недостаточно надёжен на Android), то же предупреждение про отсутствие
межпроцессной блокировки контейнера, что и на Desktop.

**Проверено по-настоящему, весь путь через реальный UI на эмуляторе, не
только компиляцией**: создание хранилища → Настройки → секция "Веб-доступ"
→ нажатие "Запустить" → **реальный системный диалог разрешения на
уведомления** (доказательство, что код действительно выполнился, а не
просто скомпилировался) → статус сменился на `Запущен: https://
10.0.2.15:8443` → `dumpsys activity services` подтвердил настоящий
foreground-сервис с уведомлением → HTTPS-запросы с хоста через
`adb forward`: `/health` → 200, `/` (index.html) → 200, `POST /api/login`
с реальными логином/паролем → 200 с `csrf_token`, `GET /api/library` с
сессионной курой → 200 `[]` (пустая, честно для только что созданного
хранилища). Кнопка "Остановить" — процесс на устройстве реально исчезает
из `ps`, порт перестаёт отвечать.

**Ложный след, разобранный до конца, а не отброшенный на "наверное
показалось"**: первая попытка логина вернула `401 auth_failed` при заведомо
верных логине/пароле — выглядело как возможный баг Argon2id/HKDF при
кросс-компиляции под Android (bionic vs glibc). Проверено честно, а не
предположено: собран отдельный минимальный Rust-бинарник (`unlock_probe`),
использующий только `cove-core` напрямую (без веб-слоя), под тот же
`x86_64-linux-android`, запущен на том же эмуляторе через `run-as` с теми
же логином/паролем на пути `--container` из логов процесса — **успешно
разблокировал контейнер**. Это доказало, что крипто-ядро на Android
корректно, и заставило искать причину дальше, а не списать на "Android
такой Android". Найдено через `ss -tlnp`: на ХОСТЕ уже висел **посторонний,
давно забытый процесс Desktop-версии `cove-web-backend`**, слушающий
`0.0.0.0:8443` ещё с более раннего разбора в этой же сессии — `adb forward
tcp:8443 tcp:8443` тихо провалился ("Address already in use", сообщение
было в выводе, но не сразу замечено), и все curl-запросы уходили не в
эмулятор, а в этот левый процесс, обслуживающий другое хранилище. После
переброса на другой локальный порт (`adb forward tcp:9443 tcp:8443`) логин
и весь остальной путь прошли с первого раза.

**Честно не проверено в этом заходе**: реальное физическое устройство
(только эмулятор), загрузка файла через веб на Android (проверены логин +
список файлов, не сама загрузка), поведение при потере Wi-Fi во время
активной сессии, несколько одновременных клиентов. Известное ограничение
межпроцессной блокировки контейнера (Фаза 13) теперь вдвойне актуально на
Android — приложение и его собственный веб-сервер работают с одним и тем
же файлом на одном устройстве без координации, то же предупреждение в UI,
что и на Desktop.

**"Подключи релоад к юи"** — то самое сознательно отложенное подключение
`AndroidContainer.reload()` к `LibraryScreen`, по прямому запросу
пользователя. Тот же принцип, что уже работает на Desktop
(`_live_sync_timer` + `_reload_and_refresh()`/`_manual_refresh()`), перенесён
на Compose:

- `reloadAndRefresh(force: Boolean = false)` — вызывает `container.reload()`
  на `Dispatchers.IO`, перерисовывает список только если `reload()` вернул
  `true` (реально были изменения) либо `force = true` (ручная кнопка должна
  ощутимо реагировать на нажатие, даже если на диске ничего не изменилось —
  тот же выбор, что `_manual_refresh()` на Desktop). `AndroidException` от
  конфликта (у сессии есть свои несохранённые правки прямо в момент опроса)
  молча пропускает тик, не считается ошибкой — тот же контракт, что и у
  Core `reload()`.
- `LaunchedEffect(Unit) { while (true) { delay(3000); reloadAndRefresh() } }`
  — тихий опрос раз в 3 секунды, пока виден экран библиотеки, тот же
  интервал, что и Desktop-таймер.
- Кнопка `IconButton` с иконкой `Refresh` в `TopAppBar` — ручной триггер
  с `force = true`.

**Проверено по-настоящему на эмуляторе, вживую, без выхода из аккаунта**
(в отличие от предыдущего захода, где загрузка подтверждалась только через
повторный вход): собран `./gradlew assembleDebug` → `BUILD SUCCESSFUL`,
установлен на эмулятор, создано новое тестовое хранилище ("livesync"),
запущен веб-сервер через реальный UI настроек (с реальным диалогом
разрешения на уведомления). Не закрывая открытую сессию библиотеки:
1. Файл `livesync_test.bin` (300 КБ) отправлен `curl`-ом на веб-сервер —
   появился в списке автоматически, без единого нажатия, в пределах
   3-секундного опроса.
2. Файл `livesync_test2.bin` (150 КБ) отправлен тем же способом, сразу
   нажата кнопка "Обновить" — список обновился немедленно, не дожидаясь
   таймера, подтверждая, что и ручной путь работает независимо от
   опроса.

Оба сценария подтверждены скриншотами с устройства. `adb forward` в этот
раз сразу настроен на нестандартный локальный порт (`9444`), с проверкой
`ss -tlnp` перед стартом — тот самый старый посторонний Desktop-процесс на
хостовом порту 8443 (см. запись выше) всё ещё висел, урок из прошлого
разбора применён заранее, а не после повторной путаницы. После теста:
сервер остановлен, `pm clear` очистил тестовое хранилище и данные веб-
сервера на эмуляторе, локальные тестовые файлы и cookie-файл удалены.

**Честно не проверено**: поведение опроса при сворачивании приложения на
фон и возврате (LaunchedEffect должен перезапуститься с рекомпозицией, но
это не проверялось отдельно), синхронизация при одновременном изменении
с обеих сторон (Android UI и его же веб-сервер) — известное ограничение
отсутствия межпроцессной блокировки (Фаза 13) применимо и здесь: конфликт
просто пропускает тик опроса, не разрешает его.

**Первая проверка на реальном физическом Android-устройстве** (по прямому
запросу пользователя — "если я подключу свой телефон ты сможешь прогнать
его по тестам?"), а не только на эмуляторе — Xiaomi/MIUI (`arm64-v8a`,
Android 13, MIUI Global 14.0.5). Не просто повтор эмуляторных тестов:
столкнулись с двумя реальными окруженческими особенностями и одним
найденным на реальном железе багом UI, ни один из которых не проявлялся
на эмуляторе.

**1. MIUI блокирует `adb shell input`/`screencap` без отдельного тумблера.**
Обычной "Отладки по USB" недостаточно: `input tap`/`keyevent` падали с
`SecurityException: требуется разрешение INJECT_EVENTS`, а `screencap`
тихо возвращал полностью чёрный кадр (даже при `mWakefulness=Awake`,
экран объективно был включён и разблокирован — не баг блокировки, а
намеренная маскировка вывода). Причина — MIUI-специфичная настройка "USB
debugging (Security settings)" в "Для разработчиков", отдельная от
базовой "USB debugging", требующая Mi-аккаунт и интернет на телефоне.
После включения пользователем — всё заработало as expected.

**2. Найден реальный баг UI, невидимый на эмуляторе: `SettingsScreen.kt`
не прокручивался.** Секция "Веб-доступ" (кнопка "Запустить") и вся секция
"Хранилище" (удаление БД) были физически недостижимы на этом телефоне —
не заслонены, а буквально не существовали в дереве интерфейса за пределами
видимой области экрана. Причина: главный `Column` в `SettingsScreen.kt`
не имел модификатора `.verticalScroll(rememberScrollState())` — на
эмуляторе (1344×2992, другая плотность) весь контент случайно помещался
на экран без скролла, а на реальном экране этого телефона (1080×2400,
другое соотношение сторон/плотность) — не помещался, и Compose просто
молча клипует лишнее, без ошибки и без индикации, что часть UI недоступна.
Диагностировано методично, не угадано: сначала подтверждено, что `input
swipe` в принципе работает на этом устройстве (успешно проскроллены
системные Android Settings), что исключило проблему ввода и указало на
сам экран Cove. Дамп `uiautomator` подтвердил отсутствие каких-либо
`scrollable="true"` узлов и что `Column` физически не содержит кнопку
"Запустить" в дереве при любой попытке проскроллить. Исправлено добавлением
`.verticalScroll(rememberScrollState())` к главному `Column`
(`SettingsScreen.kt`) — пересобрано, переустановлено, проверено вживую:
после фикса секции "Веб-доступ" и "Хранилище" стали доступны прокруткой.

**3. Реальная Wi-Fi сеть (не NAT эмулятора) изолирует клиентов друг от
друга.** Веб-сервер поднялся на реальном LAN-адресе телефона
(`https://192.168.10.16:8443`, роутер Keenetic), но прямой `curl` с хоста
(та же подсеть `192.168.10.0/24` по Ethernet) получил `No route to host`,
`ping` — 100% потерь. Не баг Cove — сетевая изоляция клиентов (AP isolation
на роутере или firewall самого телефона), то есть реалистичное
напоминание, что "тот же принцип, что и Desktop-версия" из текста
предупреждения в UI не гарантирует связность в любой сети. Обойдено тем же
способом, что и с эмулятором — `adb forward tcp:9445 tcp:8443` (туннель
через USB, не через Wi-Fi) — и уже через него подтверждён полный
реальный путь: `GET /health` → `ok` (200), `POST /api/login` с реальными
логином/паролем → 200 с `csrf_token`, `GET /api/library` с сессионной
курой → 200 с реальной записью ранее импортированного файла.

**Остальной путь, проверенный на этом же реальном устройстве, вживую, не
на эмуляторе**: создание нового хранилища через настоящую Argon2id-
разблокировку на реальном ARM64 (не эмулированном) процессоре — фраза
восстановления сгенерирована и показана; импорт JPEG через системный SAF
file picker (Android `DocumentsUI`, включая честный поиск нужного файла
среди похожих отладочных скриншотов через встроенный поиск SAF, после
двух случайных промахов мимо не того элемента списка — известная
проблема координат из более ранних заходов этой сессии, см. выше);
сгенерированная миниатюра корректно отражает содержимое реального файла;
полноэкранный просмотрщик изображений корректно расшифровывает и
показывает реальный файл на реальном экране.

**Честно не проверено**: биометрия/Keystore на этом устройстве (не
дошли), просмотрщики видео/аудио/текста (проверен только просмотрщик
изображений), поведение при реальной потере Wi-Fi, "Проверить обновления"
и "Удалить базу данных" на реальном железе (кнопки стали доступны только
после фикса скролла, отдельно не нажимались). После проверки: веб-сервер
остановлен, `adb forward` снят, `pm clear` очистил тестовое хранилище и
данные веб-сервера на телефоне, тестовый JPEG удалён из `/sdcard/Download`,
локальные cookie/JSON-файлы удалены.

**Причина сетевой изоляции с предыдущей записи найдена и устранена — не
баг Cove, а MAC-рандомизация Android.** По прямому запросу пользователя
("локальная сеть должна работать нормально") разобрано методично через
adb, а не оставлено на уровне "видимо, роутер виноват":
`adb shell cmd wifi status` показал, что телефон подключён к сети с
**рандомизированным** MAC-адресом (`useRandomizedMac=true`,
`macRandomizationSetting: 3`), который отличается от настоящего заводского
(найден через `dumpsys wifi | grep wifi_sta_factory_mac_address`). Android
с версии 10 по умолчанию генерирует новый случайный MAC для каждой Wi-Fi
сети (и периодически ротирует его), поэтому даже ранее "зарегистрированное"
в роутере устройство выглядит для роутера как новое незнакомое каждый раз
— отсюда `ip neigh show` с `FAILED` на хосте (ARP-запрос не долетал: не
IP/firewall-уровень, а L2), хотя тот же роутер с обычным ПК по Ethernet
работал нормально (там MAC статический). Не связано с VPN на хосте —
отдельно проверено через `ip rule show`: правило `suppress_prefixlength 0`
явно исключает локальную подсеть из туннеля, оставляя её маршрутизацию
через обычный Ethernet-интерфейс.

Пользователь переключил Wi-Fi-приватность сети на телефоне на "Использовать
MAC устройства" и заново зарегистрировал в роутере уже постоянный MAC.
После этого — **полный сквозной путь подтверждён напрямую по реальной
Wi-Fi сети, без единого обходного пути** (ни `adb forward`, ни USB):
`ping` — `0% packet loss`; `GET /health` → `ok` (200); `POST /api/login`
с реальными логином/паролем на новом тестовом хранилище → 200 с
`csrf_token`; `GET /api/library` с сессионной курой → 200. Это первое
доказательство, что заявленный в UI принцип "тот же, что и Desktop-версия"
реально работает на практике с обычного компьютера в той же сети, а не
только через эмулятор/USB-туннель. Хранилище и данные веб-сервера снова
очищены после теста (`pm clear`).

**Критический баг с потерей доступа к реальным данным пользователя — найден,
исправлен, но живая проверка на затронутом телефоне ещё не завершена.** По
прямому репорту пользователя ("после обновления база не открывается, даже
по отпечатку") — не тестовое хранилище, а основной телефон с реальными
файлами. Разобрано методично через фоновый код-аудит, а не угадано:

**Корень.** Коммит `936c3f0` ("Папки в category-вкладках привязываются к
категории...") дописал поле `folder_category` в конец каждой записи File
Table (`core/src/format/file_table.rs`). `decode_entry` читает записи
позиционно, без проверки версии — `format_version` в заголовке контейнера
при этом изменении формата **не был увеличен** (как и раньше, при
добавлении `mime_hint`/`thumbnail_of`), так что отличить "старую" запись
от "новой" по номеру версии невозможно. Контейнер, созданный ДО этого
коммита, физически не содержит нового хвостового байта-флага — новый код
либо упирается в конец буфера страницы, либо (в записи не последней в
странице) съедает байты, принадлежащие следующей записи. Результат —
`CoveError::FormatError` при разборе File Table, то есть **контейнер не
открывается вообще, независимо от пароля** — но только если в нём есть
хотя бы одна запись (пустой контейнер открывается нормально), поэтому баг
проявлялся не сразу и выглядел загадочно.

**Почему не помог и отпечаток.** Android `BiometricVault.kt` хранит сам
пароль (расшифрованный Keystore-ключом), не производный ключ контейнера —
при успешной биометрии просто вызывается тот же `unlock(user, pass)`, что
и при ручном вводе. Биометрия отработала корректно (верно расшифровала
верный пароль), но сам `unlock()` упал с `FormatError` — а
`LoginScreen.kt:93-99` **до фикса** ловил `AndroidException` без разбора
подтипа и всегда показывал "Неверное имя пользователя или пароль"
(оправдано для `AuthFailed` — анти-enumeration, ARCHITECTURE.md §3/
THREAT_MODEL.md §2.1 — но ошибочно применялось и к `FormatException`).
Пользователь физически не мог отличить забытый пароль от бага, хотя Core
всё это время присылал различимую категорию ошибки.

**Фикс — обратная совместимость чтения, не миграция файла.**
`core/src/format/file_table.rs`: `decode_page` теперь сначала пробует
разобрать страницу в ТЕКУЩЕЙ раскладке (с `folder_category`), и если разбор
не сошёлся **ровно** до конца буфера страницы (новый `Reader::remaining()`,
`core/src/format/wire.rs`) — откатывается на раскладку ДО добавления этого
поля. Безопасно, потому что смешения версий записей внутри одной страницы
не бывает: любая правка перезаписывает страницу целиком одним вызовом
`encode_page` (точечная запись по страницам, "Фаза 2/6") — страница либо
целиком старая, либо целиком новая. Ложного совпадения ("случайно сошлось
ровно до конца, но неверно") практически быть не может: сначала всегда
пробуется актуальная раскладка (для новых файлов срабатывает с первого
раза), откат — только при явном провале или остатке байт. Два новых теста
(`legacy_entries_without_folder_category_still_open`,
`legacy_multi_entry_page_still_opens`) вручную собирают страницу в старой
раскладке (зеркалят `encode_entry` без последнего блока) и подтверждают,
что `decode_file_table` всё равно её читает — закрывает пробел из
предыдущего код-аудита ("нет ни одного regression-теста на обратную
совместимость"). Затронуты оба пути чтения — `decode_file_table` (обычная
разблокировка) и `decode_file_table_lenient` (щадящая загрузка при частичном
повреждении) — оба идут через один и тот же `decode_page`. Все 74 теста
`cove-core` (72 старых + 2 новых) проходят чисто, включая долгий
`kill_minus_9_mid_commit_leaves_container_openable`.

**Android UI-фикс.** `LoginScreen.kt` (`finishUnlock`/
`finishUnlockWithRecovery`) теперь различает `AndroidException.AuthFailed`
(тот же анти-enumeration текст, что и раньше) от
`AndroidException.FormatException` (честное "файл повреждён или несовместим
с этой версией — пароль/фраза тут ни при чём") — стало возможно только
потому, что `AndroidException` в сгенерированных биндингах уже был
нормальным `sealed class` с различимыми подтипами (`AuthFailed`,
`FormatException`, ...), несмотря на `#[uniffi(flat_error)]` в
`bindings/android/src/lib.rs` — этот атрибут, вопреки первому впечатлению
от код-аудита, не схлопывает варианты в один плоский класс, а лишь убирает
у них вложенные структурные поля помимо текста; отдельные Kotlin-подклассы
он не отменяет. Значит фикс UI обошёлся без изменений в Rust/UniFFI слое.

**Пересобрано после фикса**: `cove-core` (4 Android ABI + x86_64 хост),
`cove-web-backend` (те же таргеты), Kotlin-биндинги перегенерированы
скриптом, Android release APK (`assembleRelease`, подписан), Python-биндинги
(`cove_core_py.so`), Linux AppImage (`Cove-x86_64.AppImage`). Desktop-путь
(`welcome_window.py`) уже и раньше показывал отдельное сообщение для
`CoveFormatError` (через `except Exception` с `str(exc)`, отдельно от
`CoveAuthError`) — то есть там баг маскировки не воспроизводился, только на
Android.

**Честно не завершено**: живая проверка на РЕАЛЬНОМ основном телефоне
пользователя (том самом, где баг воспроизвёлся) — пользователь согласился
подключить его по USB для диагностики, но на момент этой записи устройство
ещё не появилось в `adb devices`. До этого момента находка подтверждена
только кодом и синтетическими тестами (два новых юнит-теста, вручную
собирающих легаси-раскладку байт) — не воспроизведением на самом
пострадавшем файле. `unlock()` не изменяет файл на диске (только чтение,
до явного `commit()`), так что установка нового APK и попытка входа не
рискует данными пользователя, если/когда телефон подключится.

Современное кроссплатформенное приложение для безопасного хранения файлов
в собственном зашифрованном контейнере `.slr`:

- 🔐 безопасность на уровне современных криптостандартов (envelope encryption,
  Argon2id, XChaCha20-Poly1305, recovery key, независимый аудит)
- 🖥️ удобство файлового менеджера
- 🖼️ возможности медиатеки со стримингом без расшифровки на диск
- 🌐 встроенный веб-доступ с собственной моделью угроз
- 📱 поддержка Windows, Linux и Android на едином Rust-ядре
- ⚡ производительность на коллекциях 100 000+ файлов
