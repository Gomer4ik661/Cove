## Криптография — пост-квантовая гибридная схема

Android 17 (релиз ~март 2026) добавил квантово-устойчивое шифрование по
всему security-стеку ОС — отрасль явно двигается в эту сторону, не только
отдельные экспериментальные проекты. Для envelope encryption Cove (DEK,
обёрнутый по паролю/recovery-фразе) можно рассмотреть гибридную схему
**ML-KEM768 + X25519** вместо чистого X25519/HKDF — есть зрелые чистые
Rust-крейты под ML-KEM, то есть ограничение "чистый Rust, без C-зависимостей"
(FORMAT.md §10) не нарушается. Это большая работа: смена формата (version
bump), пере-обёртка keyslots, миграция существующих контейнеров — не
быстрая правка, но стоит держать в уме как направление, а не бросаться
реализовывать немедленно.

Второй, более дешёвый пункт в эту же тему (уже предлагался раньше, но
теперь подтверждён трендом): **WebAuthn/FIDO2-ключ как второй фактор именно
для веб-логина** — отрасль password/vault-менеджеров в 2026-м массово
переходит на passkeys. Отдельно стоит отметить: Android `CredentialManager`
API (единый API для passkeys/паролей/биометрии) сюда плохо ложится "в лоб" —
он создан для федеративной аутентификации с удалённой стороной (relying
party), а разблокировка Cove — чисто локальная, без сервера, которому
нужен passkey. То есть сам API не подходит напрямую, а вот сама идея
"второй публично-ключевой фактор вместо выдуманного пароля" — для веб-входа
подходит в виде обычного WebAuthn/FIDO2 (аппаратный ключ или платформенный
authenticator), это другой протокол, доступный независимо от
Android-специфичного Credential Manager.

## Публикация в Google Play (исследование, без принятия решения)

### Что нужно для публикации
- Регистрация разработчика — **$25 одноразово**, без ежегодного продления.
- **Closed testing обязателен** для личных (personal) аккаунтов, созданных
  после 13 ноября 2023: минимум **12 тестеров** (снижено с 20 в декабре
  2024), непрерывно подписанных минимум **14 дней**, прежде чем откроется
  доступ к продакшену. Организационные аккаунты и личные аккаунты, созданные
  раньше этой даты — освобождены. Прохождение теста не гарантирует
  автоматического одобрения — Google всё равно проверяет само приложение.
- **Таргет API level** — Google Play требует таргетить актуальный уровень
  Android API для новых приложений/обновлений, сейчас это диапазон около
  API 35-36 (растёт на ~1 уровень в год, нужно сверяться на момент публикации,
  а не ориентироваться на `android/app/build.gradle.kts` в этот момент
  написания).
- **Экспортный контроль / self-classification** — т.к. Google — американская
  компания, а приложение не просто использует TLS, а само шифрование —
  основная функция продукта, нужно подавать **ежегодный self-classification
  report** в US government по правилам EAR (обычно достаточно декларации
  "mass market", категория 5D002/Note 4, но саму процедуру нужно пройти, не
  просто поставить галочку в консоли).
- **Data Safety секция** в Play Console — декларировать шифрование данных
  (у Cove это легко подтвердить — ничего не передаётся нешифрованным), плюс
  аккуратно описать сетевые запросы, которые есть (веб-доступ, проверка
  обновлений на GitHub Releases).
- `FOREGROUND_SERVICE_SPECIAL_USE` и `POST_NOTIFICATIONS` в манифесте скорее
  всего потребуют явного обоснования при ревью — у нас уже есть
  `<property>`-описание в `AndroidManifest.xml` для этого сервиса, это
  правильное направление, но стоит явно сослаться на него при заполнении
  формы ревью, а не полагаться, что Google сам найдёт.

### Платное распространение
- Для продажи приложения или in-app покупок нужен **Google Payments
  merchant account** (юр. имя бизнеса, адрес, банковские реквизиты для
  выплат). Комиссия Google — **15-30%** в зависимости от типа и объёма.

### Монетизация — что делают похожие приложения
По реальным аналогам (OneVault Password Manager, Privault, LockMyPix, Inner
Gallery): в категории privacy/vault-приложений доминирует **freemium +
разовая покупка Pro** (не подписка) — пользователи этой категории
специально ищут "без подписки навсегда", это часть ценностного
предложения приватности. Разовые цены на рынке — примерно $4.99-$10
one-time за полную версию. Подписка даёт более предсказуемый доход в целом
по рынку приложений, но в этой конкретной категории может восприниматься
как противоречие философии "не вытягивать с пользователя деньги
бесконечно" — ровно та аудитория, что сравнивает с VeraCrypt/Cryptomator,
скорее насторожится от подписки.

Возможная модель под Cove конкретно: исходники остаются бесплатными и
открытыми (AGPL-3.0, как уже есть), а **платная версия в Play Store** —
это оплата за канал распространения/готовую сборку, не за код — ровно так
делает Cryptomator на iOS (ядро бесплатно и открыто, но готовое приложение
в App Store платное). Это не противоречит текущей лицензии — платным
становится только один конкретный канал дистрибуции.

## Найденный и исправленный баг: "Остановить" веб-сервер крашило всё приложение на Android

При повторной проверке веб-доступа на Android (по прямому запросу — "прогони
ещё раз" после правок в `SettingsScreen.kt`/`LibraryScreen.kt`) нажатие
кнопки "Остановить" в разделе "Веб-доступ" **крашило всё приложение
целиком**, не только сервис — воспроизведено дважды подряд на эмуляторе
(`Process com.cove.app (pid N) has died`, Activity принудительно закрыта
системой).

**Причина.** `WebServerService.kt:98-129` (`startServer()`) запускает
отдельную корутину, которая блокирующе читает stdout дочернего процесса
построчно (`proc.inputStream.bufferedReader().useLines { ... Log.i(...) } }`)
для пересылки логов в logcat. `stopServer()` (строка 165) вызывает
`proc.destroy()`, который закрывает этот поток **прямо во время**
блокирующего `read()` в читающей корутине — она получает
`InterruptedIOException: read interrupted by close() on another thread`.
Эта корутина была без единого `try/catch`, а `scope` — `SupervisorJob() +
Dispatchers.IO` без `CoroutineExceptionHandler`: `SupervisorJob` защищает
только соседние корутины от отмены, но не глушит само исключение — оно
долетает до JVM-обработчика по умолчанию и валит процесс приложения
целиком. Раньше это не заметили: более ранняя проверка в ROADMAP смотрела
только на то, что порт перестал отвечать и процесс пропал из `ps` — оба
признака одинаково верны и при штатной остановке, и при краше всего
приложения, так что по этим двум критериям баг был неотличим от успеха.

**Фикс.** Обернул читающую корутину в `try { ... } catch (_: IOException)`
— `InterruptedIOException` при намеренном `destroy()` это ожидаемое
поведение, не реальная ошибка, тихо игнорируется. Проверено вживую:
запуск → остановка → запуск → остановка подряд, `pid` приложения не
менялся ни разу, краша нет.

## Найденный баг: Корзина на Android — билет в один конец

**Исправлено.** `LibraryScreen.kt` — добавлен раздел "Корзина" в drawer
(`listTrash()`), восстановление (`restoreFile()`, иконка ↺) и диалог
подтверждения перед удалением везде (в обычных разделах — "можно
восстановить", в Корзине — "это необратимо", кнопка окончательного
удаления красным). Проверено компиляцией + полной debug-сборкой
(`./gradlew assembleDebug` — `BUILD SUCCESSFUL`); живого тапа на
устройстве/эмуляторе не было — стоит проверить руками перед релизом.

Было до фикса (для истории):

Проверено по коду (core → UniFFI-биндинги → Kotlin), не предположение:

- `core::Container::delete_file` (`core/src/container/mod.rs:977`) — это
  **переключатель**: первый вызов на записи — мягкое удаление (помечает
  `trashed = true`, восстановимо), **второй вызов на уже находящейся в
  корзине записи — окончательное удаление** (снятие записи из File Table,
  блоки становятся орфанами, место возвращается только при `compact()`).
  Так и задумано — так делает Desktop (`desktop/app/main_window.py:844`,
  с комментарием "delete_file на уже находящейся в корзине записи =
  окончательное удаление").
- `list_trash()` и `restore_file()` **полностью реализованы и экспортированы**
  в Android UniFFI-биндингах (`bindings/android/src/lib.rs:313`, `:362`,
  сгенерированный `listTrash()`/`restoreFile()` в
  `cove_core_uniffi.kt:1620`/`:1981`) — то есть на уровне Core/FFI всё готово.
- Но в `LibraryScreen.kt` — единственном экране библиотеки на Android —
  `listTrash()` и `restoreFile()` **не вызываются вообще** (0 упоминаний).
  Раздела "Корзина" в drawer нет (только Библиотека/Фото/Видео/Документы/
  Избранное/Настройки). Нажатие на иконку удаления (`LibraryScreen.kt:534`)
  сразу вызывает `container.deleteFile(entry.fileId)` **без единого
  диалога подтверждения** — файл просто пропадает из списка.

**Итог**: на Android удаление файла выглядит как обычное "удалить", но на
самом деле это мягкое удаление без подтверждения и без какого-либо способа
увидеть или восстановить файл с телефона — он залипает в невидимой корзине
навсегда (пока пользователь не откроет тот же контейнер на Desktop и не
восстановит/не добьёт удаление оттуда). Для человека, который пользуется
только телефоном, это неотличимо от потери данных при случайном нажатии —
а список кликабелен построчно, мисклик вполне реалистичен.

**Минимальный фикс**: диалог подтверждения перед `deleteFile()` на Android
(дешёво, разом снижает риск случайной потери). **Полный фикс**: экран/вкладка
"Корзина" с восстановлением — функции уже есть в биндингах, нужен только UI.

## UX

- **Индикатор прогресса импорта/экспорта файлов.** Сейчас при загрузке
  файла в хранилище не видно, что происходит и насколько это долго:
  - Desktop (`desktop/app/main_window.py`) — вызов импорта не показывает
    `QProgressDialog`/`QProgressBar` вообще, в коде ничего такого нет.
  - Android (`android/app/src/main/kotlin/com/cove/app/screens/LibraryScreen.kt:497`)
    есть только общий `CircularProgressIndicator` на весь экран (неопределённый
    спиннер), без процента/размера — то есть на крупных файлах человек не
    поймёт, зависло ли приложение или просто долго шифрует.

  Нужно: полоска прогресса с процентом (или хотя бы "X МБ из Y МБ") на
  импорте и экспорте, на обеих платформах. Технически это означает, что
  `Container::import_file`/`export_file` в `core/` должны отдавать
  прогресс через callback/канал, а не быть атомарным вызовом "всё или
  ничего" — ядро пока почти наверняка не даёт промежуточных callback'ов,
  это нужно будет сначала проверить и, если нет, добавить на уровне core.

## Безопасность — дёшево и быстро, не трогает формат контейнера

- **`FLAG_SECURE` на Android — исправлено.** Выставлен на уровне окна в
  `MainActivity.onCreate()` — покрывает все экраны сразу (приложение
  одноактивитное). Проверено сборкой, не живым устройством.
- **Отпечаток TLS-сертификата в UI.** `web/backend/src/tls.rs` генерирует и
  кэширует самоподписанный сертификат, но его SHA-256-отпечаток не
  показывается ни в desktop `settings_dialog.py`, ни в Android
  `SettingsScreen.kt` — пользователь не может сверить его при подключении
  с другого устройства (TOFU без видимого отпечатка).
- **Очистка EXIF при экспорте** (GPS, модель устройства) — опционально,
  чекбоксом. `exif` вообще не упоминается ни в desktop, ни в Android коде.
- **Предупреждение перед `compact()`** — он безвозвратно уничтожает
  orphaned-блоки, единственная копия данных — один `.slr`-файл.

## Безопасность — средний уровень

- **Keyfile как второй фактор разблокировки** (пароль + файл-ключ вместе в
  Argon2id, как в VeraCrypt) — не меняет байтовый формат контейнера, только
  вход в KDF.
- **TOTP/WebAuthn для веб-доступа** — именно для `web/`, так как это
  единственная сетевая поверхность приложения (в отличие от desktop/Android,
  где разблокировка происходит в контролируемом локальном UI). Server-side
  rate-limit на `/api/login` уже есть (`web/backend/src/auth.rs`,
  `check_login_rate_limit`, THREAT_MODEL §2.4) — второго фактора сверху нет.
- **Журнал подключений к веб-серверу с IP** — desktop "Журнал входов" не
  различает вход через GUI и через веб, IP не пишет.
- **Привязка веб-сервера не к `0.0.0.0`, а к конкретному интерфейсу/подсети**
  + явный текст в UI "не выставляйте порт наружу через проброс портов".

## Безопасность — крупнее, но осмысленно

- **Duress/decoy-пароль** — отдельный пароль открывает пустую декоративную
  версию или стирает ключевой материал текущего пользователя. Не то же
  самое, что hidden volumes VeraCrypt — дешевле архитектурно, не требует
  неотличимости от случайных данных на уровне формата.
- **Hidden/decoy volumes в стиле VeraCrypt** — самое частое, что ищут на
  форумах при сравнении с VeraCrypt. Упомянуто для полноты, но
  **не рекомендуется**: `docs/THREAT_MODEL.md` уже осознанно исключает это
  ("нет скрытых томов") — добавление будет противоречить принятому решению,
  а не чинить пробел.

## Мелочи списком

- авто-очистка поля пароля/буфера обмена через N секунд;
- версионирование последних N снэпшотов File Table перед `compact()`
  (лёгкий снэпшот, не полный бэкап) — защита от случайного подтверждения
  удаления;
- задокументировать процесс воспроизводимой (reproducible) сборки и
  опубликовать хэши релизов — подпись обновлений Ed25519 уже есть
  (Фаза 18), но именно "reproducible build + хэши" — это то, чем конкуренты
  козыряют в обзорах как доказательство соответствия бинарника исходникам.
