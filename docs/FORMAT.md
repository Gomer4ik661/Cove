# Формат контейнера `.slr` — спецификация v1

Единый источник истины по бинарной структуре. Реализация в `core/` должна
следовать этому документу; любые изменения формата — новая версия (см. §7).

## 0. Принципы (почему так, а не иначе)

1. **Всё чувствительное — зашифровано.** Имена файлов, пути, содержимое —
   ничего не течёт в открытом виде. Открытым остаётся только то, что
   объективно не может быть зашифровано (см. §1) или не является секретом
   (соли, параметры KDF — это нормально, они не секретны по определению).
2. **Один DEK на контейнер, разные ключи-обёртки на пользователя.**
   Данные шифрует один Data Encryption Key. Каждый пользователь (и
   recovery-фраза) — это отдельный "keyslot", который оборачивает тот же
   DEK своим паролем. Смена пароля = перешифровка одного маленького блока,
   а не всего контейнера.
3. **Разные ключи для разных типов данных (HKDF-разделение).** Из DEK через
   HKDF выводятся подключи под File Table, под индекс, под блоки данных.
   Это гигиена: даже теоретическая проблема в одном домене не даёт
   переиспользовать ключ в другом.
4. **XChaCha20-Poly1305 везде, где шифруем.** 192-битный nonce достаточно
   большой, чтобы генерировать его случайно на каждый вызов — не нужно
   городить счётчики и координацию между потоками/блоками.
5. **Append-mostly + copy-on-write.** Существующие блоки не перезаписываются
   на месте. Новые данные пишутся в свободное место, и только в конце —
   одна атомарная операция переключает "текущую версию" контейнера
   (см. §6). Крах процесса в любой момент не должен портить контейнер.
6. **Всё, что можно пересчитать — не критично для целостности.** Search
   Index строится из File Table, поэтому при повреждении просто
   перестраивается в фоне, а не валит открытие контейнера.

## 1. Общая раскладка файла

```
Offset 0
┌─────────────────────────────────────────────┐
│ Header                    (512 B, plaintext) │
├─────────────────────────────────────────────┤
│ Keyslots region           (plaintext struct) │  N слотов, фикс. размер
├─────────────────────────────────────────────┤
│ Commit Pointer A          (512 B)            │  двойная буферизация,
│ Commit Pointer B          (512 B)            │  см. §6
├─────────────────────────────────────────────┤
│ Superblock (v.N, v.N-1, ...)                 │  зашифровано K_meta
│   → указатели на File Table / Index / ...    │  (append, старые версии
│                                               │   переиспользуются GC)
├─────────────────────────────────────────────┤
│ File Table               (paged, encrypted)  │  K_filetable
├─────────────────────────────────────────────┤
│ Search Index             (paged, encrypted)  │  K_index, rebuildable
├─────────────────────────────────────────────┤
│ Free Block Map                               │  K_meta
├─────────────────────────────────────────────┤
│ Data Blocks region                           │  K_data, per-block nonce
│   (файлы + миниатюры как обычные записи      │
│    с internal-флагом)                        │
└─────────────────────────────────────────────┘
```

Файл — обычный файл ОС, растёт по мере необходимости (append), максимальный
размер практически не ограничен (offset'ы 64-битные).

---

## 2. Header (512 байт, plaintext)

| Поле | Размер | Описание |
|---|---|---|
| `magic` | 8 B | `"COVEfmt\0"` |
| `format_version` | u16 | версия формата контейнера |
| `container_uuid` | 16 B | уникальный ID (пригодится для sync в v1.2) |
| `created_at` | u64 | unix timestamp создания |
| `block_size` | u32 | размер чанка данных, по умолчанию 4 MiB |
| `keyslots_offset/len` | u64×2 | указатель на Keyslots region |
| `commit_a_offset`, `commit_b_offset` | u64×2 | фикс. позиции Commit Pointer'ов |
| `header_checksum` | 32 B (BLAKE3) | проверка на битые сектора (не защита от подмены — просто от порчи) |

Header пишется один раз при создании контейнера и после этого неизменен
(кроме миграции версии формата — тогда создаётся новый файл, см. §7).

---

## 3. Keyslots region (пользователи и recovery)

Фиксированное число слотов (например, 16). Пустые слоты — нули. Каждый слот:

| Поле | Размер | Описание |
|---|---|---|
| `state` | u8 | empty / active |
| `slot_type` | u8 | user / recovery |
| `username` | до 64 B | plaintext (не секрет) |
| `role` | u8 | admin / read-write / read-only |
| `kdf_salt` | 32 B | своя соль на слот |
| `kdf_params` | Argon2id: memory, iterations, parallelism | бенчмаркается на устройстве, где создан слот |
| `wrapped_dek` | 32 B ciphertext + 16 B tag | `XChaCha20-Poly1305(KEK_i, nonce_i, DEK)` |
| `wrap_nonce` | 24 B | |
| `slot_checksum` | 32 B | целостность слота |

`KEK_i = Argon2id(password_i, kdf_salt_i, kdf_params_i)`.

Recovery-слот устроен идентично обычному пользователю: "пароль" — это
recovery-фраза (BIP39-подобная, конвертируется в ключевой материал тем же
Argon2id). Это осознанное упрощение — не два разных механизма, а один,
переиспользованный.

Список пользователей для экрана логина читается без пароля (username,
role — plaintext), но `wrapped_dek` бесполезен без правильного пароля.

---

## 4. Superblock (зашифрован K_meta = HKDF(DEK, "cove.superblock.v1"))

Маленький блок, переписывается целиком при каждом commit (append новой
версии, не in-place). Содержит:

- Указатели (offset+len) на актуальные File Table, Search Index, Free Block Map
- Указатель на **резервную** копию File Table (предыдущая валидная версия —
  на случай, если текущая повреждена, см. §8)
- Монотонный `version_counter`
- Настройки контейнера (тема по умолчанию, размер миниатюр и т.п. — то,
  что раньше называлось отдельной "Фазой Settings"; выделять под это
  отдельный регион файла избыточно, это несколько байт)

---

## 5. File Table (paged, encrypted K_filetable)

Разбита на страницы фиксированного размера (например, 64 KiB), каждая —
отдельный AEAD-блок. Изменение одной записи → перезапись одной страницы,
а не всей таблицы (важно при 100k+ файлов).

Запись файла:

| Поле | Описание |
|---|---|
| `file_id` | u64, внутренний ID |
| `parent_id` | u64, ID родительской папки (дерево) |
| `name` | зашифровано вместе со страницей |
| `size`, `created_at`, `modified_at` | |
| `mime_hint` | |
| `content_hash` | BLAKE3 от расшифрованного содержимого — для целостности и дедупликации |
| `block_list` | список ID блоков данных, из которых собран файл |
| `flags` | trashed / favorite / **internal** (миниатюры хранятся как обычные записи с этим флагом — не показываются в библиотеке, но используют ту же инфраструктуру блоков) |

---

## 6. Data Blocks region

Область фиксированных слотов размера `block_size`. Каждый слот:

```
[ BlockHeader: file_id, block_index, nonce (24B), plaintext_len ]  ← plaintext
[ Ciphertext ]
[ Poly1305 tag (16B) ]
```

`BlockHeader` не зашифрован — `file_id` это внутреннее число, не имя файла,
поэтому не несёт чувствительной информации, а нужен для учёта свободного
места без расшифровки. Ключ шифрования — `K_data = HKDF(DEK,
"cove.datablocks.v1")`, nonce на каждый блок случайный (см. принцип §0.4).

Такое чанкирование даёт seek/стриминг видео: чтобы отдать плеер-байты 40–41
МБ файла, достаточно расшифровать один блок, а не весь файл.

---

## 6a. Commit Pointer — атомарность (двойная буферизация)

Два фиксированных слота `Commit Pointer A/B` рядом с Header. Каждый:

```
version_counter (u64) | superblock_offset (u64) | superblock_checksum (32B, BLAKE3)
```

Запись всегда идёт в **неактивный** слот, затем происходит один `fsync`.
При открытии контейнера сравниваются оба слота — побеждает тот, у кого
корректная checksum и больший `version_counter`. Если процесс упал между
записью Superblock и обновлением Commit Pointer — на диске остался старый,
но валидный Commit Pointer, контейнер открывается без потерь (просто
теряется последняя незакоммиченная операция, а не весь файл).

---

## 7. Версионирование формата

`format_version` в Header фиксирует layout. При изменении формата —
не in-place миграция, а: открыть старым кодом → пересобрать в новый файл
новой версией кода → атомарно подменить файл на диске (rename). Это же
даёт бесплатную компактификацию (см. ниже).

## 8. Восстановление при повреждении

Приоритет источников при открытии:
1. Commit Pointer с большим `version_counter` и валидной checksum
2. Если Superblock по этому указателю не проходит проверку — пробуем
   резервный указатель на File Table внутри самого Superblock (§4)
3. Если File Table повреждена частично (побилась одна страница) —
   остальные страницы остаются читаемыми, теряются только записи из
   повреждённой страницы (не весь каталог)
4. Search Index при любом сомнении просто перестраивается из File Table
   в фоне — он не источник истины

## 9. Free Block Map + компактификация

Учёт свободных слотов в Data Blocks region (какие `block_index` свободны
после удаления файлов). Компактификация — офлайн-операция (Фаза 15):
переписать контейнер, убрав дыры, аналогично §7.

---

## 10. Крипто-крейты

Зафиксированный выбор, чтобы не возвращаться к нему в процессе разработки.
Все — **чистый Rust, без C-зависимостей** (никаких `libsodium`-биндингов):
это прямое следствие Threat Model §2.2 (устойчивость парсера/крипто-кода к
памяти важнее гипотетической скорости C-библиотеки) и упрощает
кросс-компиляцию под Android через `cargo-ndk` — не нужно тащить и линковать
отдельно собранную C-библиотеку под каждый ABI.

| Назначение | Крейт | Почему именно он |
|---|---|---|
| Argon2id (KDF) | [`argon2`](https://crates.io/crates/argon2) (RustCrypto) | Явная поддержка id-варианта (не i/d) по RFC 9106, чистый Rust, часть экосистемы RustCrypto — де-факто стандарт в Rust-мире |
| XChaCha20-Poly1305 (AEAD) | [`chacha20poly1305`](https://crates.io/crates/chacha20poly1305) (RustCrypto) | Тип `XChaCha20Poly1305` из коробки, реализует общий `aead`-трейт, есть SIMD-ускорение |
| HKDF (разделение подключей) | [`hkdf`](https://crates.io/crates/hkdf) (RustCrypto) | Стандартная реализация HKDF-SHA256 под HKDF-подключи из §0.3 |
| Хеширование/чек-суммы | [`blake3`](https://crates.io/crates/blake3) (официальный крейт авторов алгоритма) | Референсная реализация, очень быстрая — важно при content-hash на 100k+ файлах (Фаза 15) |
| Обнуление ключей в памяти | [`zeroize`](https://crates.io/crates/zeroize) | Стандартный `#[derive(Zeroize)]`, используется почти во всей экосистеме RustCrypto — DEK/KEK/пароли оборачиваются в него всегда |
| CSPRNG (nonce, соли) | [`rand`](https://crates.io/crates/rand) + `OsRng` | Источник случайности — ОС-CSPRNG, не самодельный генератор |
| Constant-time сравнение | [`subtle`](https://crates.io/crates/subtle) | Для любых ручных сравнений секретов (например, чек-сумма recovery-фразы) — сами AEAD-крейты уже делают это внутри, `subtle` нужен только за пределами их API |

**Честно про аудит:** крейты RustCrypto не имеют единого сквозного
стороннего аудита на весь набор — но широко используются в проде (в т.ч.
крупными проектами) и отдельные компоненты проходили точечные аудиты в
рамках финансируемых RustCrypto-инициатив. Это не заменяет пункт из Фазы 18
ROADMAP.md — независимый аудит нужен для **конкретной схемы Cove**
(как эти примитивы скомпонованы в keyslots/envelope/chunking), а не для
самих примитивов по отдельности.

## Что осознанно хранится ВНЕ `.slr` (на диске приложения, не в контейнере)

| Что | Где | Почему не в контейнере |
|---|---|---|
| Настройки приложения (язык, тема, автозапуск) | обычный конфиг (JSON/TOML) в стандартной директории ОС | Не привязано к конкретному контейнеру, нужно до открытия любого файла |
| Список недавних контейнеров | тот же конфиг, **opt-in**, с кнопкой "очистить" | Пути — потенциально чувствительны (раскрывают факт существования хранилища); приложение не обязано их запоминать |
| Recovery-фраза | **нигде автоматически**. Показывается один раз при создании, пользователь сам её сохраняет | Автосохранение recovery-фразы на диск обнуляет смысл её существования |
| Логи приложения | обычные логи, но **без имён файлов, путей внутри контейнера и содержимого** — только структурные события ("контейнер X открыт", "ошибка записи блока N") | Иначе шифрование File Table бессмысленно — секрет утечёт через соседний лог-файл |
| Кэш миниатюр | **нигде снаружи** — миниатюры живут внутри контейнера как обычные записи File Table с `flags.internal` (§5) | Как побочный эффект — ОС не может сама сгенерировать превью для `.slr`, файл для неё непрозрачен |
| Веб-сессионные токены | эфемерно, в памяти или короткоживущее хранилище, живёт не дольше сессии | Не часть формата данных, не должно переживать перезапуск |
