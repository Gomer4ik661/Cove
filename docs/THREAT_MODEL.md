# Threat Model — Cove

Фиксирует, от чего Cove защищает, от чего — нет, и почему конкретные решения
в [FORMAT.md](FORMAT.md) выбраны именно так. Это не разовая бумажка — на неё
ссылается пользовательская документация в релизе (Фаза 18), поэтому список
"чего мы не защищаем" должен быть таким же явным, как список того, что защищаем.

## 1. Активы (что защищаем)

| Актив | Комментарий |
|---|---|
| Содержимое файлов | основной актив |
| Имена файлов, структура папок | Фаза 2/§0 FORMAT.md: шифруются вместе с File Table |
| Метаданные (даты, размеры, избранное, история) | тоже внутри зашифрованных страниц |
| Учётные данные (пароли, DEK, recovery-фраза) | не должны существовать в plaintext дольше, чем необходимо в памяти |
| Сам факт существования контейнера | частично — см. §4, полной анонимности формата не обещаем |

## 2. Модель нарушителя и сценарии

### 2.1 Утеря/кража устройства (офлайн-атака на файл) — основной сценарий
Атакующий имеет полную копию `.slr`, неограниченное время, но не знает пароль.
- **Защита**: Argon2id с параметрами, требующими секунды на попытку даже на
  быстром железе атакующего; XChaCha20-Poly1305 не имеет практических атак.
- **Требование**: KDF-параметры должны быть выбраны так, чтобы brute-force
  по словарю был экономически нецелесообразен — бенчмаркать при создании
  контейнера, не занижать по умолчанию ради скорости UX.

### 2.2 Вредоносный/повреждённый `.slr` (атака на парсер)
Кто-то подсовывает жертве специально испорченный файл-контейнер (социнженерия,
"вот бэкап твоих фото") в надежде на RCE через баг парсера.
- **Защита**: Rust (безопасность памяти по умолчанию) + фаззинг парсера
  (Фаза 17) + все размеры/оффсеты из Header и File Table валидируются
  против реального размера файла перед использованием.
- Header читается до аутентификации — значит именно код чтения Header
  и Keyslots обязан быть железно устойчив к мусорным значениям.

### 2.3 Вредоносное ПО на устройстве, пока контейнер разблокирован
Кейлоггер, memory scraper, второй процесс с доступом к памяти приложения.
- **Не полностью защищаем** — если ОС скомпрометирована во время активной
  сессии, злоумышленник может читать то же, что видит легитимный пользователь.
  Смягчения: `zeroize` ключей сразу после использования, минимизация времени
  жизни DEK в памяти, `mlock`/`VirtualLock` где доступно (мешает выгрузке в
  своп, но не мешает чтению памяти процесса).
- Явно фиксируем как **ограничение**, а не как "уязвимость к исправлению" —
  ни один софт такого класса не защищает от рута/полного контроля над ОС.

### 2.4 Сетевой атакующий (Web-интерфейс включён)
Отдельная модель, см. Фазу 13 ROADMAP.md: брутфорс логина (rate-limit),
CSRF, MITM в локальной сети (HTTPS, пусть и с самоподписанным сертификатом).
Web — самая широкая поверхность атаки во всём проекте, поэтому по умолчанию
**выключен** и требует явного включения администратором.

### 2.5 Принуждение к разблокировке (rubber-hose / "дай пароль")
- **Не поддерживаем в v1** — ни скрытых томов, ни правдоподобного отрицания
  наличия данных (plausible deniability), в отличие от VeraCrypt. Это
  сознательное решение по объёму работ, а не забытая деталь — должно быть
  прямо написано в пользовательской документации, чтобы никто не полагался
  на защиту, которой нет.

### 2.6 Инсайдер / легитимный пользователь с ограниченной ролью
Read-only пользователь физически видит расшифрованный контент, пока
работает с контейнером — роли ограничивают операции записи/управления
пользователями, но не могут помешать сделать скриншот или скопировать файл
через ОС, если экспорт роли разрешён.
- **Требование**: роль `read-only` явно запрещает экспорт/копирование через
  UI, но это UX-барьер, не криптографическая гарантия — документировать как
  "контроль доступа", не как "защиту от утечки".

### 2.7 Синхронизация / бэкап сторонними инструментами (Dropbox, rsync и т.п.)
Внешний синк может скопировать `.slr` в момент записи (torn read) —
особенно актуально, т.к. формат append-only с атомарным Commit Pointer
(FORMAT.md §6a) защищает от краха *приложения*, но не от стороннего процесса,
читающего файл в произвольный момент.
- **Рекомендация пользователю** (в документацию v1.0): не держать контейнер
  в папке активной синхронизации, пока он открыт. Правильная поддержка
  синхронизации — предмет v1.2 (Фаза 18, план после релиза), не v1.

### 2.8 Аппаратные атаки (cold boot, DMA, форензика чипа)
Вне скоупа v1 полностью. Требуют физического контроля над включённым
устройством и специализированного оборудования — стандартное ограничение
для программного уровня защиты, разделяем его с абсолютным большинством
аналогичных продуктов.

## 3. Границы доверия между компонентами

```
Web frontend  ──▶  Web backend (Axum)  ──▶  Core (Rust crate)
Android GUI   ──▶  UniFFI bindings     ──▶  Core
Desktop GUI   ──▶  PyO3 bindings       ──▶  Core
```

- **Core не доверяет входным данным ни от одного вызывающего слоя** — валидирует
  все размеры/индексы/пути, даже если GUI "должен был" уже провалидировать.
  Это конкретное требование к API Core, не пожелание.
- **Web backend — наименее доверенный процесс** в системе (принимает вход
  от сети). Должен работать с минимально необходимыми правами и не иметь
  прямого доступа к файловой системе за пределами открытого контейнера.
- Desktop/Android GUI доверенные (работают от имени залогиненного
  пользователя ОС), но всё равно не должны напрямую парсить `.slr` —
  единственный парсер формата — Core.

## 4. Что Cove осознанно НЕ обещает (для пользовательской документации)

- Анонимность/скрытие самого факта, что на диске лежит `.slr`-файл
  (расширение и magic bytes идентифицируют формат при целенаправленном анализе)
- Защиту при скомпрометированной/заражённой ОС во время активной сессии
- Скрытые тома / правдоподобное отрицание (в v1)
- Защиту от аппаратных атак на включённое устройство
- Защиту содержимого после того, как легитимный пользователь его экспортировал
  из контейнера во внешнюю (незашифрованную) файловую систему

## 5. Трассировка "угроза → решение"

| Угроза | Где решается |
|---|---|
| Офлайн brute-force пароля | Argon2id, параметры — FORMAT.md §3 |
| Утечка метаданных (имена, структура) | File Table зашифрована — FORMAT.md §5 |
| Порча контейнера при сбое | Commit Pointer double-buffer — FORMAT.md §6a |
| RCE через вредоносный файл | Rust + фаззинг — ROADMAP Фаза 17 |
| Брутфорс/CSRF на Web | Rate-limit, CSRF-токены — ROADMAP Фаза 13 |
| Потеря пароля без возврата данных | Recovery-keyslot — FORMAT.md §3 |
| Утечка через сторонние логи | Правило "без имён файлов в логах" — ROADMAP "Что хранится вне контейнера" |
